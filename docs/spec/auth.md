# 가입, 로그인, 팀 전환

누가 어떻게 계정을 만들고, 일반 회원이 어떻게 팀 회원이 되는지를 정한다. 권한 판정 규칙은 `docs/spec/roles-and-access.md`, 테이블은 `docs/spec/data-model.md`에 있다.

## 회원의 종류

계정의 종류를 따로 저장하지 않는다. 소속으로 정해진다.

| 부르는 이름 | 뜻 | 어떻게 되나 |
| --- | --- | --- |
| 일반 회원 | 로그인한 계정. 팀이 없다 | 직접 가입 (구글, GitHub, 이메일·비밀번호) |
| 팀 회원 | 팀에 하나 이상 속한 계정. 팀마다 팀 관리자이거나 팀원이다 | 새 팀 만들기, 초대 수락, 가입 요청 승인 |
| 운영자 | `branch_staff`에 있는 계정 | 스크립트로만 만든다. 공개 가입으로는 될 수 없다 |

한 사람이 여러 팀에 속할 수 있고, 팀마다 역할이 다를 수 있다.

## 인증 방식

- 라이브러리는 Better Auth를 직접 운영한다. 인증 테이블이 우리 DB에 들어가고 Drizzle 어댑터로 읽고 쓴다.
- Better Auth의 user 모델은 따로 테이블을 만들지 않고 `users` 테이블에 매핑한다. 다른 테이블의 `user_id`가 곧 인증된 사용자다.
- 모든 id는 uuid다. 컬럼 이름은 snake_case를 유지한다.
- 세션은 Better Auth의 DB 세션과 쿠키를 쓴다. 만료는 7일이고 하루마다 갱신한다.
- 이 문서는 결과로 지켜야 할 규칙을 정한다. 옵션 이름이 적힌 곳은 1.7.7에서 확인한 힌트다. 설치한 버전의 공식 문서에서 다시 확인하고, 이름이 달라도 규칙은 지킨다.

### 로그인 수단

| 수단 | 대상 | 규칙 |
| --- | --- | --- |
| 구글 | 일반 회원 | 첫 로그인이 곧 가입. 이름과 프로필 사진을 가져온다 |
| GitHub | 일반 회원 | 위와 같다. 이메일을 받을 수 있는 범위로 요청한다 |
| 이메일·비밀번호 | 일반 회원, 운영자 | 이메일 인증을 마쳐야 로그인된다. 비밀번호는 8자 이상 128자 이하 |

- 제공자의 환경 변수 두 개가 다 있을 때만 그 제공자를 켜고 버튼을 보여준다. 둘 다 없는 제공자는 꺼진다. 한쪽만 있으면 설정 오류로 본다. 빈 문자열은 없는 것으로 본다.
- 이메일은 소문자로 바꿔 저장하고 비교한다.
- 이름은 앞뒤 공백을 뺀 1–50자다. `image`가 들어 있는 이메일 가입 요청은 거절한다. 이 두 가지는 화면이 아니라 서버에서 강제한다. 가입 요청은 화면을 거치지 않고 `/api/auth`로 직접 올 수 있다.
- 이 검사는 가입 요청을 받는 단계의 훅(요청 before 훅)에서 한다. 사용자를 만드는 단계의 훅에서 하면, 이미 있는 이메일의 요청은 그 훅까지 가지 않아 응답이 달라지고 계정 유무가 드러난다.
- 소셜 가입에서 제공자가 준 이름이 비었으면 이메일의 `@` 앞부분을 쓰고, 50자를 넘으면 자른다.
- 이번 범위에서 쓰지 않는 Better Auth 엔드포인트(프로필 수정, 이메일 변경, 계정 삭제 등)는 꺼 둔다 (`disabledPaths`).

### 계정 연결과 선점 방지

남의 이메일로 먼저 가입해 두고 나중에 그 계정에 들어오는 것을 막는 규칙이다.

1. 제공자가 이메일을 인증되지 않은 것으로 알려주면 가입과 로그인을 모두 거절한다.
2. 이메일 인증을 마친 계정이 있는 이메일로 구글·GitHub 로그인이 오면 같은 사용자에 연결한다.
3. 이메일 인증을 마치지 않은 비밀번호 가입이 있는 이메일로 구글·GitHub 로그인이 오면 연결하지 않고 거절한다. `/login`에 "이 이메일로 시작한 가입이 있어요. 비밀번호를 재설정한 뒤 로그인해 주세요"를 보여준다. Better Auth의 기본 동작이 이것이므로 `requireLocalEmailVerified`와 `trustedProviders`는 설정하지 않는다.
4. 이메일 인증 링크를 눌러도 자동으로 로그인하지 않는다. `/login?verified=1`로 보내 가입 때 정한 비밀번호로 로그인하게 한다. 인증 메일에는 "가입한 적이 없으면 링크를 누르지 마세요"를 넣는다.
5. 이미 계정이 있는 이메일로 다시 가입 요청이 오면 새 계정을 만들지 않고 기존 비밀번호도 바꾸지 않는다. 응답은 새 가입과 같은 모양이고, 그 이메일 주소로 메일을 보낸다 (`onExistingUserSignUp`).
   - 기존 계정이 미인증이면 비밀번호 재설정 메일을 보낸다. 받은 사람이 자기 비밀번호를 새로 정하게 된다. (그 훅 안에서 재설정 요청 API를 부르면 된다.)
   - 기존 계정이 인증됐으면 "이미 가입된 이메일이에요" 안내 메일을 보낸다.
6. 비밀번호 재설정을 마치면 그 사용자의 세션을 모두 끊고 (`revokeSessionsOnPasswordReset`), 이메일도 인증된 것으로 한다 (`onPasswordReset`). 재설정 링크를 받았다는 것이 그 메일함의 주인이라는 뜻이기 때문이다.
7. 비밀번호가 있는 계정에 구글·GitHub 로그인 수단이 처음 연결될 때, 그 계정의 비밀번호 자격을 지우고 기존 세션을 모두 끊은 뒤 안내 메일을 보낸다. 남이 먼저 정해 둔 비밀번호가 인증 뒤에도 살아 있는 경우를 없애기 위해서다. 비밀번호로도 로그인하려면 재설정으로 다시 정한다. 운영자 스크립트가 만든 계정도 같은 규칙을 따른다.

통합 테스트로 확인할 불변 조건: 이메일 주인이 비밀번호 재설정을 마쳤거나 소셜 로그인으로 들어온 뒤에는, 다른 사람이 그 이메일로 먼저 정해 둔 비밀번호와 그때 만든 세션으로 들어올 수 없다. 소셜 로그인 경로로는 미인증 비밀번호 가입에 연결되지 않는다.

남는 위험: 남이 내 이메일로 가입을 시작했고, 가입한 적 없는 내가 인증 메일의 링크를 누르면, 내가 재설정이나 소셜 로그인을 하기 전까지 그 사람이 그 계정에 들어올 수 있다. 메일의 경고 문구로 줄이고, 그 이상은 이번 범위에서 다루지 않는다.

### 이메일 인증과 비밀번호 재설정

- 이메일로 가입하면 인증 메일을 보낸다. 인증 전에는 로그인되지 않는다.
- 인증 전인 계정으로 맞는 비밀번호를 넣어 로그인하면 인증 메일을 다시 보내고 `/verify-email`로 안내한다.
- 인증 메일은 `/verify-email`에서 다시 보낼 수 있다.
- 비밀번호 재설정을 요청하면 화면에는 항상 "메일을 보냈어요"만 보여준다. 그 이메일의 계정이 있는지는 드러내지 않는다.
- 가입 요청도 같다. 그 이메일의 계정이 이미 있는지는 응답의 모양, 상태 코드, id 형식 어느 것으로도 드러나지 않는다. 그래서 id 생성은 `advanced.database.generateId: 'uuid'`로 둔다. `false`로 두면 중복 가입의 응답에만 다른 모양의 id가 실려 계정 유무가 드러난다.
- 로그인 실패 문구는 이메일과 비밀번호 중 무엇이 틀렸는지 구분하지 않는다.
- 요청 제한은 Better Auth의 기본값을 쓴다 (배포 환경에서 켜진다). 끄지 않는다. 테스트용 인스턴스에서만 끌 수 있다. 저장소는 메모리다. 서버가 여러 대로 늘면 효과가 줄어드는 것은 알고 있는 한계이고 배포 전에 다시 정한다. 화면의 "60초에 한 번 다시 보내기"는 편의이고 실제 제한은 서버가 한다.

### 메일 발송

실제 발송 서비스는 아직 정하지 않았다. 인터페이스만 고정한다.

```ts
export interface EmailSender {
  send(message: { to: string; subject: string; text: string }): Promise<void>;
}
```

- `lib/email`에 둔다. 구현은 두 가지다: 콘솔(서버 로그에 받는 사람, 제목, 본문을 출력)과 테스트용 메모리(보낸 메일을 배열에 쌓음).
- 기본은 콘솔 구현이다. 콘솔 구현은 `NODE_ENV`가 `production`이면 본문을 출력하지 않고 오류를 던진다. 인증·재설정 링크가 운영 로그에 남지 않게 하려는 것이다.
- Better Auth는 메일 발송 함수의 오류를 삼키고 성공으로 응답한다. 그래서 `lib/email`이 "지금 메일을 실제로 보낼 수 있는지"를 알려주는 함수를 내보내고(배포 환경에서 콘솔 구현이면 false), false일 때 `/signup`은 이메일 양식 대신, `/forgot-password`와 `/verify-email`은 요청 양식 대신 "지금은 이메일로 가입하거나 재설정할 수 없어요. Google이나 GitHub로 계속해 주세요"를 보여준다. 실제 서비스를 연결하기 전(PFQV-65)의 배포 환경에서는 소셜 로그인과, 스크립트로 만든 운영자의 비밀번호 로그인만 된다.
- 메일 본문은 한국어 해요체, 텍스트만. 종류는 다섯 가지다: 이메일 인증, 비밀번호 재설정, 이미 가입된 이메일 안내, 소셜 로그인 연결 안내, 팀 초대.

## 세션을 읽는 방법

```ts
export type Session = { userId: string; email: string; name: string };
export async function getSession(): Promise<Session | null>;
export async function requireSession(): Promise<Session>;                 // 없으면 ActionError('UNAUTHENTICATED'). 액션과 queries용
export async function requirePageSession(next: string): Promise<Session>; // 없으면 redirect('/login?next=…'). (app) 페이지용
export async function requireOperatorPage(): Promise<Session>;            // 없으면 redirect('/admin/login'), 운영자가 아니면 redirect('/admin/login?error=not_operator'). admin 페이지용
```

- `getSession()`, `requireSession()`의 모양은 셋업 때와 같다. 안쪽만 Better Auth로 바꾼다.
- `getSession()`은 세션 쿠키가 없으면 인증 인스턴스를 만들지 않고 null을 돌려준다. DB와 `AUTH_SECRET`이 없는 환경에서도 로그인하지 않은 화면이 열려야 한다.
- 이메일 인증 여부처럼 `Session`에 없는 값은 `lib/dal`로 사용자 행을 읽어 확인한다.
- Better Auth를 직접 부르는 곳은 정해져 있다: `lib/auth/*`, `/api/auth/[...all]` Route Handler, 브라우저용 인증 클라이언트(`lib/auth/client.ts`). 인증 클라이언트는 `(auth)` 화면과 머리글의 로그아웃 버튼만 쓴다.
- 셋업 때 만든 데모 세션(`AUTH_MODE`, `floor_session` 쿠키, `createSessionCookie`, `clearSessionCookie`)은 없앤다.
- Better Auth 인스턴스는 처음 쓸 때 만든다. `DATABASE_URL`과 `AUTH_SECRET`이 없어도 `pnpm build`와 `pnpm test`는 통과해야 한다.
- 테스트는 PGlite DB와 메모리 메일 구현을 넣어 인스턴스를 만들 수 있어야 한다 (예: `createAuth({ db, email, secret, baseUrl })`).

### Cache Components와 화면 보호

Cache Components가 켜져 있다. 설치된 Next.js 문서의 `01-app/02-guides/authentication-with-cache-components.md`에서 `<Suspense>`를 두는 방법만 따른다. 그 가이드의 `use cache: private` 예시는 따르지 않는다.

- `getSession()`과 권한·소속 조회에는 `use cache`, `use cache: private`, `use cache: remote` 어느 것도 붙이지 않는다.
- 세션, 쿠키, 헤더, `params`, `searchParams`를 읽는 컴포넌트는 `<Suspense>` 아래에 둔다. `(app)`과 `admin` 레이아웃은 정적인 틀을 그리고 `{children}`을 `<Suspense>`로 감싼다.
- 레이아웃은 보호 수단이 아니다. 레이아웃은 이동할 때 다시 실행되지 않고, 페이지가 그려지는 것을 막지 못한다. `(app)`의 모든 페이지가 `requirePageSession()`을, `admin`의 모든 페이지가 `requireOperatorPage()`를 직접 부르고, `features/*/queries.ts`의 모든 함수와 모든 액션이 세션을 직접 확인한다.
- 로그인 뒤에는 원래 가려던 주소(`next`)로 돌아온다. `next`는 검사를 통과한 같은 사이트의 경로만 쓴다 (아래 "next 값 검사").
- `proxy.ts`는 보호된 경로에 세션 쿠키가 없을 때 `/login?next=<경로와 쿼리>`로 미리 보내는 용도다. 쿠키가 유효한지는 보지 않는다. 보안 경계가 아니다. 쿠키가 있다는 이유로 `/login`에서 다른 곳으로 보내는 일은 `proxy.ts`에서 하지 않는다. 오래된 쿠키가 있으면 `/`와 `/login` 사이를 끝없이 오가게 된다.
- 이미 로그인한 사용자가 `/login`, `/signup`에 오면 그 페이지가 `getSession()`으로 실제 확인한 뒤 `next` 또는 `/`로 보낸다. `/verify-email`, `/forgot-password`, `/reset-password`는 로그인한 상태로도 열린다. 로그인한 채로 재설정을 마칠 수 있어야 한다.
- 어떤 제공자가 켜져 있는지는 빌드 시점이 아니라 요청 시점에 읽는다 (`<Suspense>` 안에서).
- `<Suspense>` 아래에서 부른 `notFound()`와 `redirect()`는 틀이 먼저 전송된 뒤에 처리되므로 HTTP 상태가 200일 수 있다. 그대로 둔다.
- 인증 요청은 Better Auth의 Route Handler(`/api/auth/[...all]`)가 받는다. "Route Handler는 캐시되는 GET과 웹훅에만 쓴다"는 규칙의 예외다.

### next 값 검사

순수 함수 하나로 만들고 단위 테스트를 둔다. 통과하지 못하면 `/`를 쓴다.

- `/`로 시작한다. `//`나 `/\`로 시작하지 않는다.
- `\`와 제어 문자(탭, 개행 포함)가 없다. 퍼센트 인코딩을 한 번 푼 값에도 없다.
- `/api/`로 시작하지 않는다.
- `new URL(next, 기준 주소).origin`이 기준 주소의 origin과 같다.
- 테스트에 넣을 값: `/\evil.com`, `/%5Cevil.com`, `/\t/evil.com`(탭 문자), `https://evil.com`, `//evil.com`, `/api/auth/sign-out`은 거절. `/teams/start`, `/invite/abc?x=1`은 통과.

`next`는 `/login`에서 `/signup`으로 가는 링크와 소셜 로그인의 `callbackURL`에도 이어서 넘긴다.

### 주소

| 주소 | 그룹 | 누가 | 내용 |
| --- | --- | --- | --- |
| `/login` | `(auth)` | 비로그인 | 구글, GitHub, 이메일·비밀번호 로그인. 가입과 비밀번호 재설정으로 가는 링크 |
| `/signup` | `(auth)` | 비로그인 | 이름, 이메일, 비밀번호로 가입. 소셜 버튼도 같이 둔다 |
| `/verify-email` | `(auth)` | 비로그인 | "메일을 확인해 주세요" 안내와 다시 보내기 |
| `/forgot-password` | `(auth)` | 비로그인 | 재설정 메일 요청 |
| `/reset-password` | `(auth)` | 메일 링크 | 새 비밀번호 설정 |
| `/admin/login` | `(auth)` | 비로그인 | 운영자 로그인. 이메일·비밀번호만 |
| `/` | `(app)` | 로그인 | 홈. 팀이 없으면 "팀 회원으로 전환" 진입점 |
| `/teams` | `(app)` | 로그인 | 팀. 받은 초대, 내 팀, 보낸 가입 요청 (`docs/spec/ui.md`) |
| `/teams/start` | `(app)` | 로그인 | 팀 회원으로 전환. 새 팀 만들기와 기존 팀 가입 중 하나를 고른다 |
| `/teams/[teamId]` | `(app)` | 그 팀의 팀원 | 팀 화면. 팀 관리자는 초대와 가입 요청을 처리한다 |
| `/invite/[token]` | `(app)` | 메일 링크 | 초대 내용 확인과 수락·거절. 비로그인이면 로그인 뒤 돌아온다 |
| `/admin` | `admin` | 운영자 | 운영자 홈. 지금은 제목과 내가 운영하는 지점 이름 목록만 |

`/login`이 받는 쿼리

| 쿼리 | 보여줄 것 |
| --- | --- |
| `verified=1` | 이메일 인증이 끝났어요. 로그인해 주세요 |
| `error`가 인증 링크 만료·무효 | 인증 링크가 만료됐거나 잘못됐어요. 인증 메일을 다시 받아 주세요 (`/verify-email` 링크) |
| `error`가 계정 연결 거절 | 이 이메일로 시작한 가입이 있어요. 비밀번호를 재설정한 뒤 로그인해 주세요 |
| `error`가 제공자의 미인증 이메일 | 이메일이 인증되지 않은 계정이라 로그인할 수 없어요 |
| 그 밖의 `error` | 로그인하지 못했어요. 다시 시도해 주세요 |

- `error`가 있으면 `verified`보다 먼저 보여준다. `error`의 실제 값은 설치한 Better Auth가 붙이는 코드를 확인해서 맞춘다. 쿼리의 값을 화면에 그대로 출력하지 않는다.
- 인증 링크의 `callbackURL`은 언제나 `/login?verified=1`이다. Better Auth가 넘겨주는 `url`은 요청마다 `callbackURL`이 달라지므로(로그인 때 다시 보내는 메일은 `/`), 메일 발송 함수에서 `url`을 쓰지 않고 `token`으로 링크를 직접 만든다. 이메일 가입 경로에서는 `next`가 이어지지 않는다. 소셜 로그인의 오류는 Better Auth의 기본 오류 페이지가 아니라 `/login`으로 돌아오게 한다 (`errorCallbackURL`).
- `/verify-email`은 `?email=`이 있으면 그 주소로 다시 보내고, 없으면 이메일 입력란을 보여준다.

## 운영자 계정

- 운영자 계정은 스크립트로만 만든다.

```sh
pnpm admin:create --email ops@example.com --name "운영자 이름" --branch "강남점"
```

| 옵션 | 뜻 |
| --- | --- |
| `--email` | 필수. 소문자로 바꾼다 |
| `--name` | 새 계정이면 필수 |
| `--branch` | 필수. 지점 이름. 없는 지점이거나 같은 이름의 지점이 둘 이상이면 오류로 끝난다 |
| `--create-branch` | 지점이 없으면 만든다 (시간대는 기본값) |
| `--password` | 8–128자. 생략하면 무작위로 만들어 표준 출력에 한 번만 출력한다 |
| `--reset-password` | 이미 있는 계정의 비밀번호를 바꾼다. 이 옵션이 없으면 기존 비밀번호를 건드리지 않는다 |

- 새 계정이면 이메일을 인증된 것으로 만들고 `branch_staff`에 넣는다.
- 이미 있고 이메일 인증을 마친 계정이면 `branch_staff`만 추가한다. 이미 그 지점의 운영자여도 오류가 아니다.
- 이미 있지만 미인증인 계정이면 `--reset-password` 없이는 오류로 끝난다. 다른 사람이 그 이메일로 먼저 가입해 둔 것일 수 있어서다.
- `--reset-password`는 비밀번호 교체, 그 사용자의 세션 전부 삭제, `email_verified = true`를 한 번에 한다.
- 기존 계정에 구글·GitHub 로그인 수단이 연결돼 있으면 경고를 출력한다. 그 수단으로도 운영자 화면에 들어올 수 있다는 뜻이다.
- 스크립트의 본체는 DB와 인증 인스턴스를 주입받는 함수(`lib/auth/operators.ts`)로 만들어 PGlite로 테스트한다. 스크립트 파일은 인자를 읽고 그 함수를 부르기만 한다.
- `/admin` 아래의 모든 화면, queries, 액션은 서버에서 운영자인지 확인한다. 로그인하지 않았으면 `/admin/login`으로, 로그인했지만 어느 지점의 운영자도 아니면 `/admin/login?error=not_operator`로 보낸다.
- `/admin/login`은 로그인에 성공하면 `/admin`으로 간다. 이미 로그인한 운영자가 오면 `/admin`으로 보낸다. 운영자가 아닌 계정으로 로그인된 상태면 "운영자 계정이 아니에요"와 "홈으로", "다른 계정으로 로그인"(로그아웃)을 보여준다. 자동으로 로그아웃시키지 않는다.
- `/admin/login`은 안내용 입구일 뿐이다. 운영자는 `/login`으로도 로그인할 수 있고, 권한의 경계는 `/admin`의 서버 확인이다.

## 일반 회원에서 팀 회원으로

팀에 들어가는 길은 세 가지다. 새 팀 만들기와 가입 요청은 `/teams/start`에서 시작하고, 받은 초대는 `/teams`와 초대 링크(`/invite/[token]`)에서 수락한다. 이미 팀이 있는 사람도 다른 팀을 만들거나 들어갈 수 있다. 화면의 구성은 `docs/spec/ui.md`에 있다.

### 1. 새 팀 만들기

승인 절차가 없다. 양식을 채우고 누르면 바로 팀이 생기고, 만든 사람이 그 팀의 팀 관리자가 된다.

| 입력 | 필수 | 규칙 | 저장 위치 |
| --- | --- | --- | --- |
| 팀(회사) 이름 | 예 | 정규화한 뒤 2–40자. 같은 이름의 팀이 있으면 만들 수 없다 (대소문자 무시) | `teams.name` |
| 주 이용 지점 | 지점이 하나라도 있으면 예 | 지점 목록에서 고른다 | `teams.home_branch_id` |
| 인원 규모 | 예 | 1–1000의 정수 | `teams.headcount` |
| 담당자 연락처 | 예 | 숫자, `+`, `-`, 공백만. 숫자는 8–15자리. 숫자와 맨 앞의 `+`만 남겨 저장한다 | `teams.contact_phone` |
| 직함 | 아니오 | 앞뒤 공백을 뺀 40자 이하 | 만든 사람의 `team_members.title` |

- 이름 정규화: 유니코드 NFC, 앞뒤 공백 제거, 연속된 공백은 하나로. 저장할 때와 검색어 모두에 같은 정규화를 한다.
- 팀 생성과 팀 관리자 지정은 한 트랜잭션이다.
- 한 사람이 팀 관리자로 있는 팀은 최대 5개다. 넘으면 `LIMIT_EXCEEDED`.
- 이름이 겹치면 `TEAM_NAME_TAKEN`.
- 담당자 연락처는 그 팀의 팀 관리자에게만 내려보낸다. 일반 팀원에게 가는 응답에도 넣지 않는다. 주 이용 지점의 운영자도 볼 수 있게 할 값이지만, 운영자용 화면은 이번 범위가 아니다.
- 주 이용 지점은 참고 정보다. 권한 판정에는 쓰지 않는다.

### 2. 초대 수락

- 팀 관리자가 이메일 주소로 초대를 보낸다. 짧은 메시지를 붙일 수 있다 (200자 이하).
- 초대는 7일 뒤 만료된다. 팀 관리자는 대기 중인 초대를 취소할 수 있다.
- 같은 팀이 같은 이메일에 보낸 대기 중 초대는 하나뿐이다. 다시 보내면 이전 초대를 취소하고 새로 만든다.
- 한 팀의 대기 중 초대는 최대 50개다. 넘으면 `LIMIT_EXCEEDED`.
- 초대받은 사람은 `/teams`의 "받은 초대"나 메일의 링크(`/invite/[token]`)에서 수락하거나 거절한다.
- 수락할 수 있는 사람은 초대받은 이메일로 로그인했고 이메일 인증을 마친 계정뿐이다. 다른 계정이면 `INVITE_INVALID`.
- 만료됐거나 취소됐거나 이미 처리된 초대도 `INVITE_INVALID`.
- 수락하면 팀원(`member`)이 된다. 수락과 팀원 추가는 한 트랜잭션이다. 이미 그 팀의 팀원이면 역할을 바꾸지 않고 초대만 수락 처리하고 성공으로 돌려준다.
- 수락할 때 그 팀에 내 대기 중 가입 요청이 있으면 같은 트랜잭션에서 `approved`로 바꾼다. `decided_by`는 초대를 보낸 사람이다.
- 이미 그 팀의 팀원인 이메일에는 초대를 보낼 수 없다 (`ALREADY_MEMBER`).
- 여러 사람이 함께 쓰는 공유 초대 링크는 이번 범위가 아니다 (PFQV-59).

### 3. 가입 요청

- 일반 회원이 팀 이름으로 팀을 찾는다. 검색어는 정규화한 뒤 2–40자이고, 대소문자를 무시하고 이름에 검색어가 들어간 팀을 최대 10개 보여준다. 결과에는 팀 이름과 주 이용 지점 이름만 나온다.
- 요청을 보낼 때 메시지를 붙일 수 있다 (200자 이하).
- 팀과 사람마다 대기 중인 요청은 하나뿐이다. 이미 있으면 `ALREADY_REQUESTED`. 이미 팀원이면 `ALREADY_MEMBER`.
- 한 사람의 대기 중 요청은 최대 10개다. 넘으면 `LIMIT_EXCEEDED`.
- 요청한 사람은 대기 중인 요청을 취소할 수 있다. 남의 요청이거나 대기 중이 아니면 `NOT_FOUND`.
- 팀 관리자가 승인하면 요청한 사람이 팀원(`member`)이 된다. 승인과 팀원 추가는 한 트랜잭션이다. 거절하면 상태만 바뀐다.
- 승인할 때 그 사람의 이메일로 온 그 팀의 대기 중 초대가 있으면 같은 트랜잭션에서 수락 처리한다.
- 거절된 뒤에는 다시 요청할 수 있다.
- 검색 결과의 팀에서 내게 온 대기 중 초대가 있으면 "가입 요청" 대신 "받은 초대가 있어요"를 보여준다. 화면의 안내일 뿐이고 서버가 요청을 막지는 않는다.

### 동시 요청에 대한 규칙

같은 버튼을 두 사람이 동시에 누르거나 한 사람이 두 번 눌러도 결과가 맞아야 한다.

- 승인, 거절, 취소, 수락처럼 상태를 바꾸는 일은 "대기 중일 때만 바꾸는" 한 문장(`UPDATE … WHERE id = ? AND 대기 중 조건 RETURNING`)으로 한다. 바뀐 행이 없으면 `NOT_FOUND`(요청) 또는 `INVITE_INVALID`(초대)다. 먼저 읽고 나서 바꾸는 방식으로 하지 않는다.
- 승인·수락 트랜잭션 안에서 `team_members`에 넣을 때는 `ON CONFLICT DO NOTHING`을 쓴다. 트랜잭션 안에서 유니크 위반을 잡으면 트랜잭션이 깨진다.
- 이름 중복과 중복 요청은 사전 조회가 아니라 유니크 인덱스 위반으로 판정한다.
- 팀 5개, 초대 50개, 요청 10개 한도는 같은 트랜잭션에서 기준이 되는 행(사용자 또는 팀)을 `FOR UPDATE`로 잠근 뒤 센다.

### 누가 할 수 있나

| 동작 | 조건 |
| --- | --- |
| 새 팀 만들기 | 로그인한 누구나 |
| 팀 검색, 가입 요청 보내기·취소 | 로그인한 누구나. 취소는 요청한 본인만 |
| 받은 초대 수락·거절 | 초대받은 이메일의 본인 |
| 초대 보내기·취소, 가입 요청 승인·거절 | `can(ctx, 'team.manage_members', { teamId })`. `teamId`는 클라이언트가 보낸 값이 아니라 초대·요청 행에서 읽는다 |
| 팀 화면 보기 | 그 팀의 팀원 |

역할 변경, 내보내기, 팀 나가기는 이번 범위가 아니다 (PFQV-59).

## 홈에서 보이는 것

홈과 팀 화면의 구성은 `docs/spec/ui.md`가 정하고, 이 절과 다르면 `docs/spec/ui.md`가 맞다. 누가 무엇을 볼 수 있는지는 그대로다.

지금의 홈은 평면도가 들어오기 전의 임시 화면이다.

| 상태 | 보이는 것 |
| --- | --- |
| 팀이 없는 일반 회원 | 인사말, "팀 회원으로 전환" 카드. 받은 초대가 있으면 개수를 같이 보여준다 |
| 팀이 있는 회원 | 인사말, 내 팀 목록(팀 이름, 내 역할)과 각 팀 화면으로 가는 링크, "다른 팀 만들기·가입" 링크 |
| 운영자 | 위 내용에 더해 "운영자 화면" 링크 |

머리글에는 이름과 로그아웃이 있다.

## 액션 결과 코드 추가

`docs/spec/server.md`의 목록에 아래 네 개를 더한다.

| 코드 | 뜻 |
| --- | --- |
| `TEAM_NAME_TAKEN` | 같은 이름의 팀이 있음 |
| `ALREADY_MEMBER` | 이미 그 팀의 팀원 |
| `ALREADY_REQUESTED` | 대기 중인 가입 요청이 있음 |
| `INVITE_INVALID` | 초대가 만료·취소·처리됐거나 다른 사람의 초대 |

`LIMIT_EXCEEDED`는 예약 한도 외에 팀 5개, 대기 중 초대 50개, 대기 중 요청 10개 한도에도 쓴다.

## 환경 변수

| 이름 | 필수 | 설명 |
| --- | --- | --- |
| `AUTH_SECRET` | 실행 시 | Better Auth 비밀 키. 32바이트 이상의 무작위 값 |
| `NEXT_PUBLIC_APP_URL` | 아니오 | 인증의 기준 주소로도 쓴다. 기본값 `http://localhost:3000` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | 아니오 | 둘 다 있을 때만 구글 로그인을 켠다. 한쪽만 있으면 오류 |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | 아니오 | 둘 다 있을 때만 GitHub 로그인을 켠다. 한쪽만 있으면 오류 |

`AUTH_MODE`는 없앤다. OAuth 앱에 등록할 콜백 주소는 `{앱 주소}/api/auth/callback/google`, `{앱 주소}/api/auth/callback/github`이다.
