## 02가 끝난 뒤 직접 할 일

Codex 환경에는 실제 DB와 OAuth 앱이 없어서, 아래는 직접 해야 확인된다.

1. `.env.local`에 `AUTH_SECRET`을 넣는다. `openssl rand -base64 32`로 만든다. `AUTH_MODE`는 지운다.
2. `pnpm db:migrate`로 새 마이그레이션을 적용한다. `users.auth_id`가 없어지므로, 이미 넣어 둔 사용자 데이터가 있으면 먼저 확인한다.
3. 소셜 로그인을 쓰려면 OAuth 앱을 등록하고 값을 `.env.local`에 넣는다. 값이 없으면 그 버튼은 화면에 나오지 않고, 이메일·비밀번호만으로도 동작한다.

   | 제공자 | 등록하는 곳 | 콜백 주소 (로컬) | 환경 변수 |
   | --- | --- | --- | --- |
   | 구글 | Google Cloud Console의 OAuth 클라이언트 | `http://localhost:3000/api/auth/callback/google` | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
   | GitHub | GitHub Developer settings의 OAuth App | `http://localhost:3000/api/auth/callback/github` | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` |

   배포하면 배포 주소로 된 콜백을 하나씩 더 등록한다.
4. `pnpm dev`로 띄우고 이메일로 가입해 본다. 인증 메일은 실제로 가지 않는다. 서버 로그에 찍힌 링크를 열어 인증한 뒤, 가입 때 정한 비밀번호로 로그인한다.
5. `pnpm admin:create --email … --name … --branch …`로 운영자 계정을 만들고 `/admin/login`으로 들어가 본다. 정확한 사용법은 Codex가 `README.md`에 적는다.
6. 구글, GitHub로 각각 로그인해 본다. 같은 이메일로 두 방법을 쓰면 한 계정으로 합쳐지는지 본다.
7. 끝난 단계의 Jira 이슈(PFQV-63–66) 상태를 바꾼다.

## 04가 끝난 뒤 직접 할 일

1. `pnpm db:migrate`를 적용한다. `.env.local`에 `SEED_ALLOW_HOST=<Neon 호스트 이름>`을 적고 `pnpm db:seed`를 실행한다. 호스트 이름은 처음 실행했을 때 나오는 안내에 있다. 나중에 배포한 사이트가 쓸 DB에는 시드를 넣지 않는다. 저장소에 적힌 비밀번호의 관리자 계정이 생긴다.
2. `/admin/login`에서 `admin@floor.com` / `admin1234!`로 로그인한다. 운영 지점에 강남점과 성수점이 보여야 한다.
3. 멤버 계정으로도 로그인해 본다. 비밀번호는 모두 `floor1234!`다.

   | 이메일 | 이름 | 어떤 사람 |
   | --- | --- | --- |
   | `member@floor.com` | 김하은 | 팀이 없는 일반 회원 |
   | `design.admin@floor.com` | 박지훈 | 디자인팀 팀 관리자 |
   | `design.member@floor.com` | 이서연 | 디자인팀 팀원 |
   | `growth.admin@floor.com` | 최민준 | 그로스팀 팀 관리자 |
   | `both@floor.com` | 정유나 | 디자인팀과 그로스팀의 팀원 |

4. PFQV-14는 닫지 않는다. 작은 데모 세트만 끝난 것이고 대량 합성 데이터가 남아 있다.

시드를 다시 실행하면 예약이 그날 기준으로 옮겨지고, 화면에서 고친 시드 지점·층·공간·팀과 그 이용 대상이 원래 값으로 돌아간다. 직접 만든 데이터와 계정의 비밀번호는 건드리지 않는다. 배포 환경(`NODE_ENV=production`)에서는 실행되지 않는다.

## 05가 끝난 뒤 직접 할 일

1. `pnpm db:migrate`를 적용하고 `pnpm db:seed`를 다시 실행한다.

## 07–09 전에 한 번 해 둘 것: DB 위치

지금 Neon 프로젝트가 미국 오하이오(`us-east-2`)에 있다. 한국에서 개발 서버를 띄우면 조회 한 번에 0.2초쯤 걸리고, 화면 하나가 조회를 15–30번 하고 있어서 2–6초가 된다. 07이 조회 수를 줄이지만, 거리 자체는 코드로 줄일 수 없다.

- Neon에서 한국에 가장 가까운 곳은 싱가포르(`aws-ap-southeast-1`)다. 서울과 도쿄는 없다.
- 이미 만든 프로젝트의 위치는 바꿀 수 없다. 싱가포르에 새 프로젝트를 만들고 `DATABASE_URL`과 `SEED_ALLOW_HOST`를 바꾼 뒤 `pnpm db:migrate`와 `pnpm db:seed`를 다시 하면 된다. 지금은 시드 데이터뿐이라 옮길 것이 없다.
- 나중에 배포할 때는 서버(Vercel 함수)의 위치를 DB와 같은 곳으로 맞춘다. 서버와 DB가 멀면 같은 문제가 다시 생긴다 (PFQV-47).

## 10이 끝난 뒤 직접 할 일

1. `pnpm db:migrate`와 `pnpm db:seed`를 다시 돌린다 (사진 테이블과 사진 시드가 들어간다).
2. 층 화면을 연다. 공간 줄마다 사진이 보이고, 공간을 누르면 맨 위에서 사진을 넘겨 볼 수 있어야 한다.
3. 8층의 리뷰룸(이서연으로 로그인)은 사진 대신 자리 표시가 보여야 한다.
4. 김하은으로 7층을 연다. 전용 공간 줄에는 사진이 없고 빗금과 자물쇠만 있어야 한다.
5. PFQV-81, 82 상태를 바꾼다.

## 11이 끝난 뒤 직접 할 일

1. 층 화면을 넓은 창에서 연다. 시간표가 먼저 보여야 한다. "목록"으로 바꾼 뒤 새로 고쳐도 목록이 유지돼야 한다.
2. 날짜 줄 옆의 달력을 열어 2주 뒤를 고른다. 일요일에는 "쉼"이 보이고, 고르면 쉬는 날 안내가 나와야 한다.
3. 시간표에서 빈 칸을 누른다. 아래에 예약 줄이 뜨고, 같은 줄의 뒤 칸을 누르면 시간이 늘어나야 한다. 예약하면 그 자리에 "내 예약" 블록이 생긴다.
4. 목록에서 공간을 누른다. 하루 일정이 4–5시간 넘게 보이고(전에는 2시간쯤), 예약 양식은 아래 두 줄이어야 한다.
5. 밤(영업이 끝난 뒤)에 열어 본다. "비어 있음"이 아니라 "오늘 영업이 끝났어요"가 보여야 한다.
6. 창을 좁혀 본다. 목록이 먼저 보이고, 달력과 공간 상세가 아래에서 올라와야 한다.
7. PFQV-83, 84, 85 상태를 바꾼다.

## 12가 끝난 뒤 직접 할 일

1. "내 예약"에서 "달력"을 누른다. 예약이 있는 날에 조각이 보이고, 날짜를 누르면 오른쪽에 그날의 예약이 나와야 한다.
2. "이 날짜에 예약하기"를 누른다. 그 날짜의 층 화면으로 가야 한다.
3. 홈에서 다음 예약(사진과 큰 시간), 이번 주 내 예약, 자주 쓰는 공간을 본다.
4. 지점 목록의 카드에 사진, 숫자 셋, 요일별 운영 시간이 보이는지 본다.
5. PFQV-86, 87, 88, 89 상태를 바꾼다.

## 13이 끝난 뒤 직접 할 일

1. 넓은 창에서 층 화면의 시간표를 연다. 왼쪽의 공간 칸에 꺾쇠가 보여야 한다.
2. 공간 칸을 누른다. 오른쪽에서 공간 상세가 한 번에 열려야 한다 (열렸다 닫혔다 하면 안 된다). 사진을 넘겨 본다.
3. 닫는다. 시간표로 돌아오고 아래에 그 공간의 예약 줄이 보여야 한다.
4. 빈 칸을 눌러 시간을 고르고, 제목을 적은 뒤 같은 공간의 칸을 누른다. 상세에 그 시간과 제목이 들어 있어야 한다. 닫아도 예약 줄에 남아 있어야 한다.
5. 창을 좁혀 공간 칸을 누른다. 지금처럼 아래에서 시트가 올라와야 한다.
6. PFQV-91 상태를 바꾼다.

- `pnpm lint && pnpm typecheck && pnpm test && pnpm build`가 내 컴퓨터에서도 통과하는가
- 건너뛴(`skip`) 테스트가 없는가

- `AUTH_MODE`, `floor_session`, `createSessionCookie`가 코드에 남아 있지 않은가
- 로그아웃한 상태로 `/`, `/teams/start`, `/admin`을 열면 로그인 화면으로 가는가
- 운영자가 아닌 계정으로 `/admin`을 열면 막히는가
- `/login?next=https://example.com`처럼 바깥 주소를 넣어도 바깥으로 보내지 않는가
- `/login?next=/\evil.com`도 마찬가지인가
- 가입 화면에서 이미 있는 이메일을 넣었을 때, 그 이메일이 가입돼 있다는 것이 드러나지 않는가
- 인증 링크를 눌렀을 때 바로 로그인되지 않고 로그인 화면으로 가는가
- 이메일로 가입한 계정에 Google로 로그인한 뒤, 예전 비밀번호로는 로그인되지 않는가
- 팀원(관리자 아님) 계정으로 팀 화면을 열었을 때 담당자 연락처가 보이지 않는가

- 다른 사람 이메일로 온 초대 링크를 열었을 때 수락되지 않는가
- 지시서에 없는 의존성이 늘지 않았는가 (`package.json`). 02에서 늘어나는 것은 `better-auth`와 스크립트 실행 도구 정도이고, 04에서는 시간대 계산용 `date-fns` 계열이 늘 수 있다

04–06에서 더 볼 것

- 컴퓨터의 시간대를 다른 곳으로 바꿔도 예약 시간이 지점 시간(서울)으로 보이는가
- 관리자가 아닌 계정으로 `/admin/branches/…` 주소를 직접 열면 막히는가
- 주소의 지점·층 id를 다른 지점 것으로 바꿨을 때 고칠 수 없는가
- 층의 이용 대상을 좁혔을 때 그 층 공간의 이용 대상이 같이 정리되는가

## 이 자료에서 새로 정한 것 (예약 2차)

직접 정해 준 것: 좌석은 오전·오후·종일 단위, 좌석 배치도에서 직접 고르기, 사용 인원은 선택 입력이고 정원을 넘으면 막기, 인원으로 공간 거르기, 예약의 시간·인원 바꾸기, 회의실 예약에 사람을 이름이나 이메일로 찾아 초대하기, 초대받으면 머리글의 알림으로 알려 주기, 예약 시작 30분·10분·5분 전과 시작할 때 알림.

아래는 그것을 구현할 수 있게 채워 넣은 것이다. 바꾸려면 Codex에게 넘기기 전에 `docs/spec/booking-2.md`를 고치면 된다.

| 정한 것 | 이유 |
| --- | --- |
| 오전과 오후는 13:00에서 나눔. 오후 1시가 지나면 종일은 고를 수 없음 | 구간을 따로 저장하지 않고 시간으로 판정해서 지금의 겹침 제약을 그대로 씀 |
| 좌석은 한 사람이 같은 시간에 한 자리. 회의실의 하루 한도에 세지 않음. "며칠 앞"만 같은 값 | 종일이 14시간이라 분으로 세는 한도와 맞지 않음 |
| 좌석의 접근은 구역을 따름 | 좌석 행마다 이용 대상을 두면 운영자가 관리할 수 없음 |
| 배치도에 누가 예약했는지 보여주지 않음 | 조회를 늘리지 않고 노출도 줄임 |
| 배치는 평면도 문서의 좌석 위치에서 줄과 칸을 뽑아 격자로 그림 | 평면도 렌더러가 아직 없음. 들어오면 이 자리를 바꿔 끼움 |
| 좌석 예약이 남은 구역은 보관할 수 없음 | 구역이 보관되면 좌석 예약이 보이지 않는 채로 남음 |
| 인원 조건은 주소(`people`)에만 두고 클라이언트가 거름 | 조회 결과가 같아서 서버에 다시 물을 이유가 없음 |
| 사람 찾기는 같은 팀 사람(이름·이메일 일부)과 이메일 전체가 일치하는 사람만. 이메일은 가려서 내려보냄 | 아무 글자로 가입자 전체를 훑을 수 없게 |
| 참석자는 20명까지, 같은 팀이 아닌 사람은 5명까지, "나 + 참석자"는 정원까지. 수락·거절 없음 | 초대가 스팸 통로가 되지 않게. 단계는 단순하게 |
| 초대받은 예약은 공간 이름은 보여주고 사진과 링크는 없음 | 접근할 수 없는 공간의 사진을 내려보내지 않는 규칙을 그대로 지킴 |
| 알림은 그때의 내용을 담아 저장. 미리 알림은 예약할 때 보일 시각을 적어 미리 넣어 둠 | 주기적으로 도는 서버 작업이 없음. 읽는 조회가 쓰지 않아도 됨 |
| 같은 예약의 미리 알림은 가장 최근 것 하나만 보이고, 예약이 끝나면 사라짐 | 목록과 읽지 않은 수가 미리 알림으로 가득 차지 않게 |
| 알림 수는 60초마다, 창으로 돌아올 때, 다음 알림 시각에 맞춰 다시 읽음. 새 알림은 토스트도 | 실시간 연결이 아직 없음 (PFQV-19) |
| 참석자 찾기와 알림만 Route Handler(GET)로 읽음 | 액션은 한 번에 하나씩 실행돼 입력을 따라가지 못하고, 화면 전체를 다시 읽으면 낭비 |
| 예약 바꾸기는 본인만, 같은 공간·같은 날짜 안에서. 시작한 뒤에는 시간을 못 바꿈. 좌석 예약은 바꾸기 없음 | 규칙을 만들 때와 같게 유지. 연장은 PFQV-36 |
| 예약을 쓰는 액션은 관련된 사용자 행을 id 순서로 잠금 | 서로를 초대하는 두 예약이 동시에 들어와도 교착이 생기지 않게 |
| 예약 행은 언제나 사용자 행 뒤에 잠금 ("참석 안 함"도) | 예약 바꾸기(사용자 → 예약)와 "참석 안 함"이 반대 순서로 잠가 교착이 생기지 않게. 지금의 취소도 이 순서다 |
| 예약을 바꿀 때 같은 팀이 아닌 사람 5명 한도는 새로 넣는 사람이 있을 때만 봄 | 이미 참석자인 사람은 다시 따지지 않는다는 규칙과 어긋나지 않게 |
| 동시성 테스트는 잠금 함수에 끼어들어 "먼저 끝난 변화"를 넣는 지금의 방식으로, 교착은 잠금 순서로 확인 | PGlite는 연결이 하나라 두 요청을 정말로 동시에 돌릴 수 없다. 실제 Postgres에서의 교착은 테스트로 재현하지 못한다 |

알고 있는 한계: 사람 찾기의 요청 제한이 메모리에 있어 서버가 여러 대면 효과가 줄어든다. 이메일 전체가 맞으면 그 계정이 있다는 것과 이름이 드러난다. 배포 전에 제한기의 저장소를 정해야 한다.

## 이 자료에서 새로 정한 것 (앱의 틀과 채팅)

직접 정해 준 것: 디스코드·슬랙처럼 채팅·화상 통화·자료 공유, 팀으로 묶되 모르는 사람과도 대화, 통화는 음성 채널과 허들 둘 다, 실시간은 Ably, 파일 저장소는 나중에, 메시지는 읽음·안 읽음·수정·삭제·리액션, 채팅 화면은 메시지 화면과 오른쪽 시트 둘 다, 틀은 레일 + 사이드바. Ably와 LiveKit Cloud의 키는 `.env.local`에 넣어 두었다.

채팅의 정의와 채워 넣은 것은 `docs/spec/chat.md` 끝의 표에 있다. 앱의 틀(지시서 19)에서 정한 것:

| 정한 것 | 이유 |
| --- | --- |
| 사이드바는 1280px 이상에서만 본문 옆에 서고, 그보다 좁으면 "메뉴"로 여는 서랍 | 레일과 사이드바가 320px를 쓰므로 1024px부터 세우면 층 화면의 목록과 420px 패널이 들어가지 않음 |
| 문서 전체가 스크롤되고, 레일과 사이드바만 화면에 붙음. 위 줄은 붙지 않음 | 지금의 붙는 패널, 예약 줄, 스크롤 복원을 고치지 않으려고 |
| 알림 종은 위 줄 한 곳에만 | 두 곳에 그리면 다시 읽기와 토스트가 두 번 돔 |
| 사이드바 접기와 그 기억은 하지 않음 | 쿠키를 레이아웃에서 읽으면 틀 전체가 요청을 기다리게 됨 (Cache Components) |
| 레일의 Floor 아이콘은 `aria-current="true"`, 사이드바 메뉴만 `page` | 한 화면에 "지금 페이지"가 둘이 되지 않게 |
| 768px 미만의 아래 탭은 지금 네 개 그대로. "메시지"는 지시서 20에서 | 채팅이 없는 동안 빈 탭을 두지 않음 |

## 아직 정하지 않은 것

- 실제 사진으로 바꿀지. 바꾼다면 `public/seed/photos/`의 파일을 같은 이름으로 갈아 끼우거나, `seed-photos.json`의 경로를 고치면 된다
- 운영자가 사진을 올릴 때 쓸 파일 저장소 (PFQV-90)

- 실제 메일 발송 서비스. 배포 전에 정한다 (PFQV-65에 남김)
- 팀 만들기에 운영자 승인을 둘지. 지금은 승인 없음
- 주 이용 지점이 권한에 영향을 줄지. 지금은 참고 정보
- 요청 제한의 저장소(지금은 메모리), 인증을 끝내지 않고 방치된 가입을 언제 지울지
- 로그인·가입 화면과 운영자 공간 관리 화면의 시안. 문구와 구성만 `docs/spec/ui.md`에 있다. 팀 화면은 2차에서 다시 그리지 않았다 (`ui-*.png` 그대로)
- 시드 계정의 이메일 도메인. `floor.com`은 남이 가진 실제 도메인일 수 있어서, 실제 메일 서비스를 붙이기 전에 시드 계정에 메일이 나가지 않게 하거나 주소를 바꿔야 한다
- 행동 기록(누가 언제 무엇을 했는지)을 따로 쌓을지. 지금은 쌓지 않는다
- 배포한 사이트에서 관리자 화면을 어떻게 보여줄지 (데모 계정, PFQV-46)
