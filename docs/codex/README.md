# Codex에게 맡기는 방법

이 폴더는 Codex에게 작업을 넘길 때 쓰는 자료다. 사람이 읽는 안내는 이 파일 하나이고, 나머지는 Codex가 읽는다.

## 지시서

| 번호 | 파일 | 내용 | 상태 |
| --- | --- | --- | --- |
| 01 | `docs/codex/01-setup.md` | 기본 셋업 (뼈대, DB 스키마, 권한 함수, 토큰) | 끝남 |
| 02 | `docs/codex/02-auth.md` | 가입과 로그인 (Better Auth, 이메일 인증, 운영자 계정) | 끝남 |
| 03 | `docs/codex/03-team-join.md` | 일반 회원에서 팀 회원으로 (새 팀 만들기, 초대, 가입 요청) | 끝남 |

## 02가 끝난 뒤 직접 할 일

Codex 환경에는 실제 DB와 OAuth 앱이 없어서, 아래는 직접 해야 확인된다.

1. `.env.local`에 `AUTH_SECRET`을 넣는다. `openssl rand -base64 32`로 만든다. `AUTH_MODE`는 지운다.
2. `pnpm db:migrate`로 새 마이그레이션을 적용한다. `users.auth_id`가 없어지므로, 이미 넣어 둔 사용자 데이터가 있으면 먼저 확인한다.
3. 소셜 로그인을 쓰려면 OAuth 앱을 등록하고 값을 `.env.local`에 넣는다. 값이 없으면 그 버튼은 화면에 나오지 않고, 이메일·비밀번호만으로도 동작한다.

   | 제공자 | 등록하는 곳 | 콜백 주소 (로컬) | 환경 변수 |
   | --- | --- | --- | --- |
   | 구글 | Google Cloud Console의 OAuth 클라이언트 | `http://localhost:3000/api/auth/callback/google` | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` |
   | GitHub | GitHub Developer settings의 OAuth App | `http://localhost:3000/api/auth/callback/github` | `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` |

   배포하면 배포 주소로 된 콜백을 하나씩 더 등록한다.
4. `pnpm dev`로 띄우고 이메일로 가입해 본다. 인증 메일은 실제로 가지 않는다. 서버 로그에 찍힌 링크를 열어 인증한 뒤, 가입 때 정한 비밀번호로 로그인한다.
5. `pnpm admin:create --email … --name … --branch …`로 운영자 계정을 만들고 `/admin/login`으로 들어가 본다. 정확한 사용법은 Codex가 `README.md`에 적는다.
6. 구글, GitHub로 각각 로그인해 본다. 같은 이메일로 두 방법을 쓰면 한 계정으로 합쳐지는지 본다.
7. 끝난 단계의 Jira 이슈(PFQV-63–66) 상태를 바꾼다.

## 04가 끝난 뒤 직접 할 일

1. `pnpm db:migrate`를 적용한다. `.env.local`에 `SEED_ALLOW_HOST=<Neon 호스트 이름>`을 적고 `pnpm db:seed`를 실행한다. 호스트 이름은 처음 실행했을 때 나오는 안내에 있다. 나중에 배포한 사이트가 쓸 DB에는 시드를 넣지 않는다. 저장소에 적힌 비밀번호의 관리자 계정이 생긴다.
2. `/admin/login`에서 `admin@floor.com` / `admin1234!`로 로그인한다. 운영 지점에 강남점과 성수점이 보여야 한다.
3. 멤버 계정으로도 로그인해 본다. 비밀번호는 모두 `floor1234!`다.

   | 이메일 | 이름 | 어떤 사람 |
   | --- | --- | --- |
   | `member@floor.com` | 김하은 | 팀이 없는 일반 회원 |
   | `design.admin@floor.com` | 박지훈 | 디자인팀 팀 관리자 |
   | `design.member@floor.com` | 이서연 | 디자인팀 팀원 |
   | `growth.admin@floor.com` | 최민준 | 그로스팀 팀 관리자 |
   | `both@floor.com` | 정유나 | 디자인팀과 그로스팀의 팀원 |

4. PFQV-14는 닫지 않는다. 작은 데모 세트만 끝난 것이고 대량 합성 데이터가 남아 있다.

시드를 다시 실행하면 예약이 그날 기준으로 옮겨지고, 화면에서 고친 시드 지점·층·공간·팀과 그 이용 대상이 원래 값으로 돌아간다. 직접 만든 데이터와 계정의 비밀번호는 건드리지 않는다. 배포 환경(`NODE_ENV=production`)에서는 실행되지 않는다.

## 05가 끝난 뒤 직접 할 일

1. `pnpm db:migrate`를 적용하고 `pnpm db:seed`를 다시 실행한다.
2. 김하은으로 로그인 → "공간 예약하기" → 강남점 7층. 회의실 A는 "전용 공간"으로만 보이고, 회의실 D는 점검 중이고, 8층 탭은 없어야 한다.
3. 회의실 C를 30분 예약한다. 개인 한도가 하루 2시간이라, 이미 있는 1시간과 합쳐 1시간 30분이 되고 "30분 남음"이 보여야 한다.
4. 브라우저 두 개로 같은 시간을 동시에 예약해 본다. 한쪽은 "방금 다른 예약이 들어왔어요"가 나와야 한다.
5. "내 예약"에서 취소한다.
6. 이서연으로 로그인해 8층 디자인 스튜디오를 디자인팀 이름으로 예약한다. 최민준으로는 회의실 A를 그로스팀 이름으로 예약한다.
7. PFQV-23, 62, 69, 70 상태를 바꾼다. PFQV-22, 25는 일부만 끝난 것이므로 닫지 않는다.

## 06이 끝난 뒤 직접 할 일

1. `pnpm db:migrate`를 적용한다.
2. 관리자로 로그인 → 강남점 → 6층에 회의실을 하나 더한다. 김하은으로 그 회의실이 보이고 예약되는지 본다.
3. 관리자로 그 회의실을 보관해 본다. 예약이 있어서 막혀야 한다. 예약을 취소한 뒤에는 보관된다.

## 결과를 볼 때 확인할 것

Codex의 보고만 믿지 말고 아래는 직접 본다.

- `pnpm lint && pnpm typecheck && pnpm test && pnpm build`가 내 컴퓨터에서도 통과하는가
- 건너뛴(`skip`) 테스트가 없는가
- `app/`, `features/` 아래 파일이 `@/lib/db`를 직접 import하지 않는가 (`lib/auth/auth.ts`만 예외)
- `AUTH_MODE`, `floor_session`, `createSessionCookie`가 코드에 남아 있지 않은가
- 로그아웃한 상태로 `/`, `/teams/start`, `/admin`을 열면 로그인 화면으로 가는가
- 운영자가 아닌 계정으로 `/admin`을 열면 막히는가
- `/login?next=https://example.com`처럼 바깥 주소를 넣어도 바깥으로 보내지 않는가
- `/login?next=/\evil.com`도 마찬가지인가
- 가입 화면에서 이미 있는 이메일을 넣었을 때, 그 이메일이 가입돼 있다는 것이 드러나지 않는가
- 인증 링크를 눌렀을 때 바로 로그인되지 않고 로그인 화면으로 가는가
- 이메일로 가입한 계정에 Google로 로그인한 뒤, 예전 비밀번호로는 로그인되지 않는가
- 팀원(관리자 아님) 계정으로 팀 화면을 열었을 때 담당자 연락처가 보이지 않는가
- 팀원(관리자 아님) 계정으로 초대 보내기·요청 승인이 서버에서 거절되는가
- 다른 사람 이메일로 온 초대 링크를 열었을 때 수락되지 않는가
- 지시서에 없는 의존성이 늘지 않았는가 (`package.json`). 02에서 늘어나는 것은 `better-auth`와 스크립트 실행 도구 정도이고, 04에서는 시간대 계산용 `date-fns` 계열이 늘 수 있다

04–06에서 더 볼 것

- 김하은으로 강남점 7층을 열고 브라우저의 네트워크 응답을 검색했을 때 "회의실 A"라는 글자가 없는가 (전용 공간의 이름이 응답에 실리지 않아야 한다)
- 남의 예약에 제목이 보이지 않고 이름만 보이는가
- 컴퓨터의 시간대를 다른 곳으로 바꿔도 예약 시간이 지점 시간(서울)으로 보이는가
- 관리자가 아닌 계정으로 `/admin/branches/…` 주소를 직접 열면 막히는가
- 주소의 지점·층 id를 다른 지점 것으로 바꿨을 때 고칠 수 없는가
- 층의 이용 대상을 좁혔을 때 그 층 공간의 이용 대상이 같이 정리되는가

## 이 자료에서 새로 정한 것 (가입·로그인·팀 가입)

직접 정해 준 것: Better Auth 직접 운영, 구글·GitHub·이메일·비밀번호, 운영자는 스크립트로 생성, 전환 페이지에서 새 팀을 만들면 승인 없이 팀 관리자, 초대와 가입 요청, 팀 정보 4가지, 메일은 인터페이스만.

아래는 그 결정을 구현할 수 있게 채워 넣은 것이다. 마음에 들지 않으면 Codex에게 넘기기 전에 `docs/spec/auth.md`를 고치면 된다.

| 정한 것 | 어디에 | 이유 |
| --- | --- | --- |
| "일반 회원 / 팀 회원 / 운영자"는 계정에 저장하지 않고 소속으로 계산 | `auth.md` | 한 사람이 여러 팀과 지점에 속할 수 있고, 팀을 나가면 저절로 일반 회원으로 돌아감 |
| 인증 테이블을 따로 두지 않고 Better Auth의 사용자를 기존 `users`에 연결 | `data-model.md` | 예약·메시지의 외래 키가 그대로 유지됨. `auth_id`는 없앰 |
| 이메일 가입은 인증 링크를 누른 뒤 비밀번호로 로그인해야 함. 링크만으로는 로그인되지 않음 | `auth.md` | 남이 내 이메일로 먼저 가입해 둔 계정에 내가 인증만 해 주는 일을 막음 |
| 같은 인증된 이메일의 구글·GitHub·비밀번호는 한 계정으로 합침. 인증을 끝내지 않은 가입이 있는 이메일은 소셜 로그인으로 연결하지 않고, 비밀번호 재설정을 거치게 함 | `auth.md` | 계정 선점 공격 방지. Better Auth의 기본 동작과 같음 |

| 메일의 콘솔 출력은 개발에서만. 배포 환경에서는 오류 | `auth.md` | 인증·재설정 링크가 운영 로그에 남지 않게. 메일 서비스를 붙이기 전에는 배포 환경에서 소셜 로그인만 됨 |
| 팀 이름은 대소문자와 공백 차이를 무시하고 유일 | `data-model.md`, `auth.md` | 가입 요청할 팀을 이름으로 찾기 때문. 비슷한 이름의 가짜 팀을 막음 |
| 한 사람이 관리자인 팀은 5개, 팀의 대기 중 초대는 50개, 한 사람의 대기 중 가입 요청은 10개까지 | `auth.md` | 승인이 없으므로 무한 생성만 막음 |

| 초대와 가입 요청은 팀·상대마다 대기 중인 것 하나만 | `data-model.md` | 중복 발송과 중복 승인을 DB가 막음 |

## 이 자료에서 새로 정한 것 (목 데이터·예약·공간 관리)

직접 정해 준 것: 관리자 계정 `admin@floor.com`(비밀번호는 8자 규칙에 맞춰 `admin1234!`), 예약 화면은 공간 목록 + 타임라인 먼저, 운영자는 양식으로 지점·층·공간 관리.

아래는 그것을 구현할 수 있게 채워 넣은 것이다. 바꾸려면 Codex에게 넘기기 전에 `docs/spec/booking.md`, `docs/spec/space-admin.md`, `docs/spec/examples/seed.json`을 고치면 된다.

| 정한 것 | 어디에 | 이유 |
| --- | --- | --- |
| 사용자가 고른 층·날짜·공간은 저장하지 않고 주소에 둠. 저장하는 것은 "주로 쓰는 지점"(`users.default_branch_id`) 하나 | `booking.md` | 새로고침과 공유에 강하고, 저장할 것이 줄어듦 |
| 행동 기록 테이블은 두지 않음. 예약의 취소 시각과 취소한 사람만 예약 행에 남김 | `booking.md`, `data-model.md` | 팀 관리자나 운영자가 대신 취소했을 때 누가 했는지 알아야 함 |
| 예약은 30분 단위, 하루 안에서, 운영 시간 안에서만. Jira(PFQV-22)에는 15분 단위로 적혀 있었음 | `booking.md` | 타임라인 칸과 한도 계산이 단순해짐. 칸의 길이는 상수 하나라서 15분으로 바꾸려면 `booking.md`의 숫자와 시드의 시각만 맞추면 됨 |
| 모든 시간 계산은 지점의 시간대 기준 | `booking.md` | 서버와 브라우저의 시간대가 달라도 같은 결과 |
| 지점의 운영 시간은 요일별로 저장. 비어 있으면 09:00–22:00 | `booking.md` | 스크립트로 막 만든 지점도 바로 예약되게 |
| 전용 공간은 허용된 팀 이름으로만 예약. 개인으로는 안 됨 | `booking.md` | "누구 자격으로 쓰는가"가 예약에 남고, 팀 한도가 적용됨 |
| 하루 한도는 같은 지점의 예약만 합산 | `booking.md` | 한도 설정이 지점별이기 때문 |
| 남의 예약은 시간과 이름만 보이고 제목은 본인·같은 팀·운영자에게만 | `booking.md` | 회의 제목에 민감한 내용이 들어갈 수 있음 |
| 자기 예약은 권한 설정과 상관없이 언제나 취소할 수 있음 | `booking.md` | 운영자가 권한을 꺼도 자기 예약을 못 지우는 상태가 생기지 않게 |
| 첫 버전에서 뺀 것: 좌석 예약, 시간 변경, 끌어서 예약, 즉시 반영, 실시간 갱신 | `booking.md` | 예약이 끝까지 돌아가는 것을 먼저. 각각 Jira에 남아 있음 |
| 공간은 지우지 않고 보관. 앞으로의 예약이 있으면 보관 불가 | `space-admin.md` | 지난 예약의 기록이 남아야 하고, 예약한 사람이 모르게 사라지면 안 됨 |
| 같은 층에서 공간 이름은 유일 | `data-model.md` | 목록에서 구분이 안 되는 공간을 막음 |
| 층의 이용 대상을 좁히면 그 층 공간의 설정을 자동으로 맞춤. 맞출 팀이 없으면 닫힘으로. 층을 닫아도 공간의 설정은 남겨 둠 | `space-admin.md` | "공간은 층보다 넓을 수 없다"가 지켜지면서, 고친 결과가 누구에게도 전보다 넓어지지 않게 |
| 이용 대상을 바꿔도 이미 있는 예약은 취소하지 않음 | `space-admin.md` | 운영자가 모르는 사이 예약이 사라지지 않게 |
| 지점 만들기는 화면이 아니라 스크립트와 시드로만. 시간대는 고칠 수 없음 | `space-admin.md` | 운영자는 지점 단위라, 지점을 만드는 사람이 따로 필요함 |
| 공간 관리는 `space.manage`, 이용 대상은 `plan.edit` 권한 | `space-admin.md` | 기본 권한표의 뜻을 그대로 따름 |
| 시드 계정 6개와 지점 2곳(강남점 6·7·8층, 성수점 2·3층). 8층은 디자인팀 전용, 성수점 3층은 닫힘 | `seed.json` | 역할과 이용 대상의 모든 경우를 화면에서 볼 수 있게. Jira(PFQV-14)가 계획한 대량 합성 데이터(지점 3, 좌석 약 600, 예약 약 6,000건)는 만들지 않았고 통계·부하 작업 때 더함 |
| 시드는 배포 환경에서 실행되지 않고, 로컬이 아닌 DB에는 `SEED_ALLOW_HOST`로 허용한 호스트에만 들어감 | `04-seed.md` | 저장소에 적힌 비밀번호의 계정이 공개 사이트에 생기지 않게 |
| 결과 코드 2개 추가: `OUTSIDE_HOURS`, `SPACE_IN_USE` | `server.md` | 화면이 이유를 구분해 알려 줄 수 있게 |

## 아직 정하지 않은 것

- 실제 메일 발송 서비스. 배포 전에 정한다 (PFQV-65에 남김)
- 팀 만들기에 운영자 승인을 둘지. 지금은 승인 없음
- 주 이용 지점이 권한에 영향을 줄지. 지금은 참고 정보
- 요청 제한의 저장소(지금은 메모리), 인증을 끝내지 않고 방치된 가입을 언제 지울지
- 로그인·가입·전환 페이지, 지점 목록, 내 예약, 운영자 공간 관리 화면의 시안. 지금은 문구와 구성만 명세에 있고, Codex는 디자인 토큰과 shadcn 기본 컴포넌트로 만든다
- 시드 계정의 이메일 도메인. `floor.com`은 남이 가진 실제 도메인일 수 있어서, 실제 메일 서비스를 붙이기 전에 시드 계정에 메일이 나가지 않게 하거나 주소를 바꿔야 한다
- 행동 기록(누가 언제 무엇을 했는지)을 따로 쌓을지. 지금은 쌓지 않는다
- 배포한 사이트에서 관리자 화면을 어떻게 보여줄지 (데모 계정, PFQV-46)
