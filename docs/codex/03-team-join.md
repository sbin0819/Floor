# 작업 지시서 03 — 일반 회원에서 팀 회원으로

지시서 02(가입과 로그인)가 끝난 뒤에 한다. 02의 커밋이 없으면 시작하지 말고 알린다.

## 목표

로그인한 일반 회원이 팀 회원이 되는 세 가지 길을 만든다. 끝났을 때 아래가 모두 참이어야 한다.

- 홈에서 "팀 회원으로 전환"으로 들어가 새 팀을 만들면, 승인 없이 바로 그 팀의 팀 관리자가 된다.
- 팀 관리자가 이메일로 초대를 보내고, 초대받은 사람이 수락하면 팀원이 된다.
- 일반 회원이 팀을 찾아 가입 요청을 보내고, 팀 관리자가 승인하면 팀원이 된다.
- 위 동작의 권한과 중복·만료 규칙이 서버에서 지켜지고 테스트로 확인된다.

## 단계

### 1. 스키마 변경과 마이그레이션

`docs/spec/data-model.md`를 따른다. 새 마이그레이션을 만든다.

- `teams`: `home_branch_id`, `headcount`, `contact_phone` 추가. 이름의 대소문자 무시 유니크 인덱스(`teams_name_unique`), `teams_headcount_valid` CHECK.
- `team_members`: `title` 추가. PK의 이름은 이미 `team_members_team_id_user_id_pk`다. 바꾸지 않는다.
- `team_invites`: `message`, `declined_at`, `revoked_at` 추가. `team_invites_one_pending` 부분 유니크 인덱스, `(email)` 인덱스.
- `team_join_requests` 테이블과 `join_request_status` enum, `team_join_requests_one_pending` 부분 유니크 인덱스.
- 이미 있는 팀 이름이 유니크 인덱스와 충돌할 수 있는 실제 데이터는 아직 없다. 데이터를 고치는 마이그레이션은 쓰지 않는다.
- `tests/db/constraints.test.ts`에 "테스트로 확인할 제약" 11–14를 더한다.
- `pnpm db:generate`를 다시 돌렸을 때 새 파일이 생기지 않아야 한다.

### 2. 데이터 접근 계층과 결과 코드

- `lib/actions/result.ts`에 결과 코드 네 개를 더한다: `TEAM_NAME_TAKEN`, `ALREADY_MEMBER`, `ALREADY_REQUESTED`, `INVITE_INVALID`.
- 유니크 인덱스 위반(SQLSTATE `23505`)은 제약 이름으로 구분해서 코드로 바꾼다: `teams_name_unique` → `TEAM_NAME_TAKEN`, `team_join_requests_one_pending` → `ALREADY_REQUESTED`. 제약 이름은 오류의 `cause` 사슬에서 찾는다. PGlite가 제약 이름을 주지 않으면 멈추지 말고, 어떤 값으로 구분했는지 보고에 적는다.
- `docs/spec/auth.md`의 "동시 요청에 대한 규칙"을 DAL에서 지킨다: 상태 변경은 조건이 붙은 `UPDATE … RETURNING` 한 문장, 트랜잭션 안의 `team_members` 삽입은 `ON CONFLICT DO NOTHING`, 한도는 기준 행을 `FOR UPDATE`로 잠근 뒤 센다. `team_invites_one_pending` 위반(다시 초대가 동시에 두 번 온 경우)은 한 번 다시 시도한다.
- 팀 이름과 검색어의 정규화(NFC, 앞뒤 공백 제거, 연속 공백 하나로)는 순수 함수 하나로 만들어 zod 스키마와 검색이 같이 쓴다. 단위 테스트를 둔다.
- `lib/dal/teams.ts`: 필요한 함수만 만든다. 예: 팀 만들기(팀과 관리자 소속을 한 트랜잭션으로), 내 팀 목록, 팀과 팀원 목록, 이름으로 팀 찾기, 초대 만들기(이전 대기 중 초대 취소 포함)·취소·수락·거절, 내 이메일로 온 대기 중 초대, 가입 요청 만들기·취소·승인·거절, 팀의 대기 중 요청, 내가 보낸 요청.
- DAL 함수는 권한을 판정하지 않는다. 권한은 액션의 `authorize`와 queries에서 판정한다.
- 팀 찾기는 이름과 주 이용 지점 이름만 돌려준다. `contact_phone`과 `headcount`는 포함하지 않는다. 대소문자를 무시하고, 검색어의 `%`, `_`, `\`는 글자 그대로 다룬다.
- 팀 화면용 조회는 `contact_phone`을 뺀 것과 넣은 것을 따로 둔다. 넣은 것은 팀 관리자에게만 쓴다.
- 초대 토큰은 암호학적으로 안전한 무작위 값(32바이트 이상)으로 만든다.

### 3. 새 팀 만들기

`features/teams/`에 `schema.ts`, `actions.ts`, `queries.ts`, `components/`를 둔다.

- 입력 규칙은 `docs/spec/auth.md`의 "새 팀 만들기" 표 그대로 zod 스키마로 만든다. 같은 스키마를 양식과 액션이 같이 쓴다.
- 주 이용 지점은 지점이 하나라도 있으면 필수다. 보낸 `homeBranchId`가 실제 지점인지 서버에서 확인한다.
- `authorize: 'none'`(로그인만 필요). 한 사람이 팀 관리자로 있는 팀이 5개면 `LIMIT_EXCEEDED`.
- 연락처는 숫자와 맨 앞의 `+`만 남겨 저장한다. 이름은 정규화한 값을 저장한다.
- 성공하면 새 팀의 id를 돌려주고, 화면은 `/teams/[teamId]`로 간다.
- 테스트: 팀과 관리자 소속이 함께 생긴다. 이름이 대소문자만 다르거나 공백만 다르면(`"Acme"`, `"acme "`, `"Acme  Inc"`와 `"Acme Inc"`) `TEAM_NAME_TAKEN`. 6번째 팀은 `LIMIT_EXCEEDED`. 없는 지점 id는 `INVALID_INPUT`. 로그인하지 않으면 `UNAUTHENTICATED`. 같은 이름으로 동시에 두 번 만들면 하나만 성공한다.

### 4. 가입 요청

- 팀 찾기는 읽기이므로 Server Action으로 만들지 않는다. 검색어를 주소의 쿼리(`?q=`)로 두고 Server Component의 queries에서 읽는다.
- 요청 보내기: 이미 팀원이면 `ALREADY_MEMBER`, 대기 중 요청이 있으면 `ALREADY_REQUESTED`, 없는 팀이면 `NOT_FOUND`, 내 대기 중 요청이 10개면 `LIMIT_EXCEEDED`.
- 요청 취소: 요청한 본인만. 남의 요청이거나 대기 중이 아니면 `NOT_FOUND`.
- 승인·거절: `can(ctx, 'team.manage_members', { teamId })`로 판정한다. `teamId`는 클라이언트가 보낸 값이 아니라 요청 행에서 읽는다. 대기 중이 아닌 요청은 `NOT_FOUND`.
- 승인은 한 트랜잭션이다: 상태를 `approved`로, `decided_by`와 `decided_at`을 채우고, `team_members`에 `member`로 넣는다. 그 사이 이미 팀원이 됐으면 요청만 승인 처리한다. 그 사람의 이메일로 온 그 팀의 대기 중 초대가 있으면 같이 수락 처리한다.
- 테스트: 요청 → 승인 → 팀원. 요청 → 거절 → 다시 요청 가능. 중복 요청. 팀원이 아닌 사람과 일반 팀원의 승인 시도는 `FORBIDDEN`. 다른 팀의 팀 관리자가 승인 시도하면 `FORBIDDEN`. 남의 요청 취소는 `NOT_FOUND`. 같은 요청을 두 번 승인하면 두 번째는 `NOT_FOUND`이고 팀원 행은 하나다. 11번째 대기 중 요청은 `LIMIT_EXCEEDED`.

### 5. 초대 보내기와 수락

- 초대 보내기(팀 관리자): 이메일과 메시지. 이메일은 소문자로 바꾼다. 그 이메일의 사용자가 이미 팀원이면 `ALREADY_MEMBER`. 같은 이메일에 대기 중 초대가 있으면 이전 것을 취소하고 새로 만든다. 팀의 대기 중 초대가 50개면 `LIMIT_EXCEEDED`.
- 커밋 뒤에 초대 메일을 보낸다 (`lib/email`, 템플릿 추가). 본문에는 팀 이름, 보낸 사람 이름, 메시지, `/invite/[token]` 링크, 만료일이 들어간다. 메일 발송이 실패해도 초대는 남기고 실패를 로그에 남긴다.
- 초대 취소(팀 관리자): 대기 중인 것만.
- 받은 초대: 내 이메일과 같고, 대기 중이고, 만료되지 않은 초대. 내 계정의 이메일이 인증된 경우에만 보인다. 인증 여부는 `Session`에 없으므로 `lib/dal`로 사용자 행을 읽어 확인한다.
- 수락·거절: `docs/spec/auth.md`의 "초대 수락" 규칙대로. 조건에 맞지 않으면 모두 `INVITE_INVALID` 하나로 돌려준다 (초대가 있는지, 누구 것인지를 드러내지 않는다). 수락은 한 트랜잭션이다.
- 이미 그 팀의 팀원인 사람이 수락하면 역할을 바꾸지 않고 초대만 수락 처리하고 성공으로 돌려준다.
- 수락할 때 그 팀에 내 대기 중 가입 요청이 있으면 같은 트랜잭션에서 `approved`로 바꾼다. `decided_by`는 초대를 보낸 사람이다.
- 테스트: 초대 → 수락 → 팀원. 다른 이메일의 계정이 토큰으로 수락 시도 → `INVITE_INVALID`. 만료·취소·거절된 초대 수락 → `INVITE_INVALID`. 다시 초대하면 이전 초대가 취소된다. 같은 초대를 두 번 수락하면 두 번째는 `INVITE_INVALID`이고 팀원 행은 하나다. 이메일 인증을 마치지 않은 계정의 수락 → `INVITE_INVALID`. 일반 팀원의 초대 시도 → `FORBIDDEN`. 다른 팀 관리자가 남의 팀 초대를 취소 → `FORBIDDEN`. 메모리 메일에 초대 메일이 한 통 쌓이고 링크의 토큰이 맞다.

### 6. 화면

색은 토큰만 쓰고 문구는 `docs/spec/auth.md`의 "화면 문구"를 쓴다. 세션, `params`, `searchParams`를 읽는 부분은 `<Suspense>` 아래에 둔다. 모든 페이지가 `requirePageSession()`을 직접 부르고, queries의 함수도 각자 세션을 확인한다. 목록이 비었을 때의 문구를 빠뜨리지 않는다.

홈 (`/`)

- `docs/spec/auth.md`의 "홈에서 보이는 것" 표대로 만든다.
- 팀이 없으면 "팀 회원으로 전환" 카드 하나가 화면의 중심이다. 받은 초대가 있으면 "받은 초대 N개"를 카드에 같이 보여준다.

전환 페이지 (`/teams/start`)

- 제목 "팀 회원으로 전환". 아래에 세 구역을 이 순서로 둔다.
- 받은 초대: 팀 이름, 보낸 사람, 메시지, 만료일, "수락"과 "거절". 없으면 구역을 접지 말고 "받은 초대가 없어요"를 보여준다.
- 새 팀 만들기: 양식과 "팀 만들기" 버튼. 승인 없이 바로 만들어진다는 한 줄 안내를 둔다. 연락처가 누구에게 보이는지도 입력 아래에 적는다.
- 기존 팀에 가입 요청: 검색 입력, 결과 목록(팀 이름, 주 이용 지점), 각 결과에 "가입 요청". 이미 팀원인 팀은 "이미 팀원이에요", 내게 온 대기 중 초대가 있는 팀은 "받은 초대가 있어요"를 버튼 대신 보여준다 (화면의 안내일 뿐이다). 내가 보낸 대기 중 요청은 목록으로 따로 보여주고 "요청 취소"를 둔다.

팀 화면 (`/teams/[teamId]`)

- 그 팀의 팀원만 볼 수 있다. 아니면 `notFound()`로 처리한다 (팀이 있는지 드러내지 않는다). 없는 팀과 팀원이 아닌 팀의 화면이 같아야 한다. `<Suspense>` 아래라서 HTTP 상태가 200일 수 있는데 그대로 둔다.
- 머리글: 팀 이름, 팀원 수, 내 역할.
- 팀원 목록: 이름, 이메일, 역할, 직함. 역할은 글자로만 보여준다 (바꾸는 기능 없음).
- 팀 관리자에게만 보이는 것: 초대 보내기 양식(이메일, 메시지), 보낸 초대 목록(대기 중, "초대 취소"), 받은 가입 요청 목록(이름, 이메일, 메시지, "승인"과 "거절"), 담당자 연락처. 화면에서 숨기는 것이 아니라 queries가 역할에 따라 이 값들을 아예 읽지 않는다. 일반 팀원에게 가는 응답(RSC 페이로드 포함)에 `contact_phone`, 보낸 초대, 가입 요청이 없어야 한다.
- 승인·거절·취소처럼 되돌리기 어려운 동작 뒤에는 결과를 토스트로 알리고 목록을 새로 읽는다.

초대 링크 (`/invite/[token]`)

- 로그인하지 않았으면 `/login?next=/invite/[token]`으로 보낸다 (`requirePageSession`과 `proxy.ts`가 한다). 로그인이나 소셜 가입을 마치면 이 주소로 돌아와야 한다. 이메일로 새로 가입한 경우에는 `next`가 이어지지 않으므로, 로그인 뒤 홈의 "받은 초대 N개"에서 찾는다. 초대 메일 본문에 이 안내를 한 줄 넣는다.
- 쓸 수 있는 초대면 팀 이름, 보낸 사람, 메시지와 "수락", "거절"을 보여준다. 수락하면 팀 화면으로 간다.
- 쓸 수 없는 초대면 "이 초대는 더 이상 쓸 수 없어요"만 보여준다. 이유를 구분해서 알리지 않는다.

공통

- 양식은 zod 스키마로 검사하고, 오류는 입력 아래에 보여주며 `aria-describedby`로 잇는다.
- 액션은 TanStack Query mutation 안에서 부르고, 한 번에 하나만 보낸다. 버튼을 연달아 눌러도 중복 요청이 나가지 않게 한다.
- 컴포넌트 테스트(`tests/unit/*.test.tsx`)를 최소한 팀 만들기 양식에 둔다: 필수 값 오류, 서버가 돌려준 `TEAM_NAME_TAKEN` 표시.

### 7. 문서와 마무리

- `README.md`에 팀 전환 흐름과 주소를 짧게 더한다.
- `tests/e2e`는 더하지 않는다. 실제 DB가 없어 로그인한 상태의 흐름을 돌릴 수 없다.
