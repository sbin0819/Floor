# 작업 지시서 04 — 목 데이터와 관리자 계정

## 목표

명령 하나로 개발용 DB에 가상 데이터와 계정이 들어가게 한다. 끝났을 때 아래가 모두 참이어야 한다.

- 여러 번 실행해도 행이 늘지 않고, 예약은 실행한 날 기준으로 다시 놓인다.
- 배포 환경과, 허용하지 않은 DB에서는 실행되지 않는다.

화면은 만들지 않는다.

## 단계

### 1. 시간 도우미, 운영 시간 스키마, 편의 시설 목록

`docs/spec/booking.md`의 "시간 규칙"과 "운영 시간"을 따른다. 모두 순수 함수이고 `server-only`를 넣지 않는다.

- `lib/time/zoned.ts`: 시간대를 받아 계산하는 함수. 최소한 아래가 필요하다.
  - 어떤 시각이 그 시간대에서 며칠인지 (`YYYY-MM-DD`)와 무슨 요일인지
  - 그 시간대의 날짜와 `HH:mm`으로 시각(`Date`) 만들기. `24:00`은 다음 날 0시다
  - 날짜에 며칠 더하기
- `lib/time/open-hours.ts`: `OpenHours` 타입과 zod 스키마, 어떤 날짜의 운영 시간 구하기 (쉬는 날이면 null, 키가 없으면 기본값 09:00–22:00, 형식이 틀린 값이면 기본값).
- `lib/spaces/amenities.ts`: 편의 시설 키 여섯 개와 한국어 이름.
- `lib/db/schema`의 `branches.open_hours` 타입을 `OpenHours`로 바꾼다. 컬럼은 그대로이므로 마이그레이션이 생기지 않아야 한다.
- 시간대 계산을 `Intl`로 직접 만들어도 되고 `date-fns`와 `@date-fns/tz`를 더해도 된다. 어느 쪽이든 서버의 시간대(`TZ`)와 무관하게 같은 결과가 나와야 한다.
- 단위 테스트: `Asia/Seoul`의 자정 앞뒤, `24:00`, 달과 해가 바뀌는 날, `America/New_York`의 서머타임 시작일과 종료일(하루가 23시간, 25시간인 날의 0시와 정오), 운영 시간의 기본값·쉬는 날·잘못된 값. 테스트는 `TZ=UTC`와 `TZ=America/Los_Angeles`에서 같은 결과여야 한다 (적어도 한 테스트가 시간대 가정 없이 돈다는 것을 보인다).

### 2. 시드 데이터 읽기와 검증

- `lib/seed/data.ts`: 세 JSON 파일을 읽어 하나의 타입 있는 값으로 합친다. `seed.json`의 `floors[].source`와 `accessGrants[].source`가 가리키는 7층 데이터는 `gangnam-7f.spaces.json`에서 가져온다 (층, 공간 33개, 팀 이름, 허용 팀). 7층 공간의 편의 시설은 `gangnam7fAmenities`로 덮어쓴다.
- zod로 검증한다. 정의하지 않은 키는 거부한다.
- 교차 검사: 모든 `floorId`, `spaceId`, `teamId`, `branchId`, `parentId`, `userKey`, `createdByKey`가 실제 항목을 가리킨다. 편의 시설은 여섯 개 키 안에 있다. 운영 시간이 스키마를 통과한다. 예약의 시작·끝이 30분 단위이고 시작 < 끝이다. `floorPlans[].documentFile`의 문서가 `lib/floor-plan`의 스키마를 통과하고 그 안의 `spaceId`가 모두 그 층의 공간이다.
- 검증에 실패하면 어느 항목이 왜 틀렸는지 알려주고 아무것도 쓰지 않는다.
- 단위 테스트: 실제 파일이 통과한다. 참조가 깨진 경우 몇 가지가 각각 실패한다.

### 3. 시드 실행 함수와 DAL

`lib/seed/run-seed.ts`에 `runSeed({ db?, auth?, now, resetPasswords })`를 만든다. DB와 인증 인스턴스와 현재 시각을 주입받고, 무엇을 몇 건 넣었는지 돌려준다. `db`와 `auth`는 생략할 수 있고, 생략하면 `withTransaction`과 `getAuth()`의 기본값을 쓴다 (`lib/seed/`와 `scripts/`는 `lib/db`를 import할 수 없다). `lib/auth/operators.ts`의 `createOperator`가 같은 모양이다.

전체가 한 트랜잭션이다. 중간에 실패하면 아무것도 남지 않는다. 트랜잭션 안의 모든 DAL 호출과 계정 준비 도우미 호출에는 그 트랜잭션 핸들을 넘긴다. 하나라도 기본 연결로 나가면 PGlite에서는 멈춘다.

계정

- 계정은 인증 인스턴스의 계정 준비 도우미(운영자 생성이 쓰는 것)로 만든다. `auth_accounts`에 직접 쓰지 않는다. 도우미가 운영자 전용 이름이면 이름을 일반화해서 같이 쓴다.
- 이메일로 찾아서 없으면 만든다: 이메일 인증된 상태, `seed.json`의 이름과 비밀번호.
- 이미 있고 이메일 인증을 마친 계정이면 이름과 비밀번호를 건드리지 않는다.
- 이미 있지만 미인증인 계정이면 `resetPasswords` 없이는 실패한다. 다른 사람이 그 이메일로 먼저 가입해 둔 것일 수 있어서다 (`docs/spec/auth.md`의 "운영자 계정"과 같은 규칙).
- `resetPasswords`가 true면 시드 계정 모두의 비밀번호를 `seed.json`의 값으로 바꾸고, 세션을 끊고, 이메일을 인증된 것으로 한다.
- `userKey`는 이렇게 만든 사용자의 id로 바꿔서 쓴다.

데이터

- 넣는 순서: 계정 → 지점 → 층 → 공간(구역 먼저, 좌석 나중) → 팀 → 팀 소속 → 운영자 → 허용 팀 → 평면도 → 층의 `published_plan_id` → 점검 → 예약.
- 지점, 층, 공간, 팀은 id로 넣고, 이미 있으면 시드의 값으로 덮어쓴다. 시드를 다시 돌리면 화면에서 고친 시드 행이 원래대로 돌아간다는 뜻이다. 공간의 `archived_at`도 null로 되돌린다.
- 팀 소속과 운영자는 이미 있으면 역할과 직함만 맞춘다. 시드에 없는 소속은 지우지 않는다.
- 시드의 층과 공간에 대한 허용 팀은 시드의 목록과 같게 맞춘다 (없는 것은 넣고 남는 것은 지운다). 이용 대상이 원래대로 돌아가려면 허용 팀도 같이 돌아가야 한다.
- 평면도는 그 id가 이미 있으면 건드리지 않는다. 그 층에 다른 게시된 평면도가 이미 있으면 넣지 않고 `published_plan_id`도 바꾸지 않는다.
- 그 밖에 시드에 없는 행은 지우지 않는다.
- 시드의 id가 아닌 행이 유니크 제약을 먼저 차지하고 있으면(같은 이름의 팀, 같은 지점의 같은 층 번호 등) 어느 행과 부딪혔는지 알려주고 실패한다.

예약과 점검

- 기준일은 지점마다 구한다: 그 지점 시간대의 오늘(`now` 기준). 오늘이 쉬는 날이면 다음 운영일이다.
- `dayOffset`은 달력의 날 수가 아니라 기준일부터 쉬는 날을 건너뛰고 센 운영일 수다. 토요일에 실행하면 강남점의 `dayOffset: 1`은 일요일(쉬는 날)이 아니라 월요일이다. 점검의 `startDayOffset`, `endDayOffset`도 같다.
- `dayOffset`과 현지 시각을 1단계의 도우미로 시각으로 바꾼다. 기준일과 운영일을 구하는 함수는 순수 함수로 두고 단위 테스트를 둔다 (성수점처럼 주말을 모두 쉬는 지점 포함).
- 시드의 예약 id와 점검 id에 해당하는 행을 먼저 지우고 다시 넣는다. 그래서 다시 실행하면 예약이 그날 기준으로 옮겨진다. "예약은 지우지 않는다"는 규칙의 예외이고, 시드가 자기 id의 행을 지우는 것만 된다.
- 확정 예약은 넣기 전에 같은 공간의 겹치는 확정 예약을 조회해서, 있으면 그 시드 예약은 건너뛰고 건수를 결과에 넣는다. 취소된 예약(`status: "cancelled"`)은 그대로 넣는다. (시드는 혼자 도는 스크립트라 사전 조회로 충분하다. 트랜잭션 안에서 겹침 제약 위반을 내면 전체가 깨진다.)
- 예약 화면의 규칙(한도, 운영 시간)은 적용하지 않고 그대로 넣는다. 데이터가 규칙을 지키게 만들어져 있다.
- `bookings[].cancelledByKey`는 검증만 하고 아직 쓰지 않는다. 취소 기록 컬럼은 05에서 생기고, 그때 시드 함수가 채우게 고친다.

DAL

- 시드가 쓰는 쓰기 함수는 `lib/dal/seed.ts`에 둔다. 다른 기능이 쓰지 않는다는 것을 파일 맨 위에 적는다.

통합 테스트 (`tests/db`, PGlite)

- 한 번 실행한 뒤 표마다 행 수가 파일과 맞는다: 지점 2, 층 5, 공간 47(7층 33 + 그 밖 14), 팀 2, 팀 소속 5, 운영자 2, 허용 팀 2, 평면도 1, 예약 9(확정 8, 취소 1), 점검 1, 계정 6.
- 두 번 실행해도 행 수가 같다.
- `admin@floor.com`이 `admin1234!`로 로그인되고 두 지점의 운영자다. 나머지 계정은 `floor1234!`로 로그인되고 이메일이 인증된 상태다.
- 7층의 `published_plan_id`가 넣은 평면도를 가리키고 상태가 `published`다.
- `now`를 수요일 낮으로 주면 `dayOffset: 0`인 예약이 그날의 현지 시각에 놓인다. `now`를 일요일로 주면 강남점의 예약은 월요일과 화요일에 놓인다. `now`를 토요일로 주면 `dayOffset: 1`인 예약이 월요일에 놓인다. 어느 경우에도 쉬는 날에 놓인 예약이 없다.
- `now`를 바꿔 다시 실행하면 예약이 새 기준일로 옮겨지고 건수는 같다.
- 시드 예약 자리에 다른 확정 예약이 먼저 있으면 그 예약만 건너뛰고 나머지는 들어간다.
- 같은 이름의 팀이 다른 id로 먼저 있으면 실패하고 아무것도 쓰이지 않는다.
- 다시 실행해도 기존 계정의 비밀번호는 그대로다 (비밀번호를 바꿔 둔 뒤 실행해서 확인). `resetPasswords`면 `seed.json`의 값으로 돌아오고 기존 세션이 끊긴다.
- `admin@floor.com`으로 가입만 해 둔 미인증 계정이 먼저 있으면 실패하고 아무것도 쓰이지 않는다. `resetPasswords`면 성공하고 그 계정의 예전 비밀번호로는 로그인되지 않는다.
- 시드의 공간에 시드에 없는 허용 팀을 넣어 둔 뒤 실행하면 그 행이 지워진다.
- 넣은 데이터로 접근 판정이 기대대로 나온다: 김하은(팀 없음)은 강남점 8층과 성수점 3층에 접근하지 못하고, 이서연(디자인팀)은 8층에 접근하고, 회의실 A는 그로스팀만 접근하고, 관리자는 모두 접근한다. `canAccessFloor()`와 `canAccess()`로 확인한다.

### 4. 스크립트와 `pnpm db:seed`

- `scripts/seed.ts`와 인자를 다루는 함수를 `scripts/admin-create*.ts`와 같은 방식으로 나눠 만든다. 실행 방법(`server-only` 조건, `tsx`, `--env-file-if-exists`)도 같게 한다.
- 옵션: `--reset-passwords`, `--help`.
- `NODE_ENV`가 `production`이면 실행하지 않고 이유를 알린 뒤 종료 코드 1로 끝난다.
- DB의 호스트가 `localhost`나 `127.0.0.1`이 아니면, 환경 변수 `SEED_ALLOW_HOST`의 값과 정확히 같을 때만 실행한다. 다르면 호스트 이름과 함께 "이 DB에 시드를 넣으려면 `.env.local`에 `SEED_ALLOW_HOST=<호스트>`를 적어 주세요"를 알리고 끝난다. 배포한 사이트와 같은 DB에 저장소에 적힌 비밀번호의 운영자 계정이 생기는 것을 막기 위해서다. `SEED_ALLOW_HOST`는 `lib/env.ts`와 `.env.example`에 더한다.
- 위 두 검사는 DB에 접속하기 전에 한다.
- `DATABASE_URL`이나 `AUTH_SECRET`이 없으면 무엇이 필요한지 알리고 끝난다.
- 시작할 때 어느 DB에 쓰는지 호스트 이름만 출력한다. 연결 문자열 전체나 비밀번호를 출력하지 않는다.
- 끝나면 넣은 건수, 건너뛴 예약 수, 계정의 이메일 목록을 출력한다. 계정의 비밀번호는 출력하지 않고 "비밀번호는 README에 있어요"라고만 알린다.
- 단위 테스트: 배포 환경 거절, 허용하지 않은 호스트 거절, `SEED_ALLOW_HOST`가 같으면 통과, `localhost` 통과, 환경 변수 누락, `--help`, 알 수 없는 옵션, 정상 실행 시 출력에 비밀번호와 연결 문자열이 없음.

### 5. 문서와 마무리

- `README.md`: 시드 사용법, `SEED_ALLOW_HOST`, 넣는 데이터의 요약, 계정 표(이메일, 비밀번호, 어떤 사람인지), 다시 실행하면 무엇이 원래대로 돌아가는지, 배포 환경에서는 실행되지 않는다는 것, 배포한 사이트가 쓰는 DB에는 시드를 넣지 말라는 경고.
- `README.md`에 주의 한 줄: 시드 계정의 이메일 도메인은 실제로 메일을 받을 수 있는 주소가 아니다. 실제 메일 서비스를 붙이기 전에 시드 계정에 메일이 나가지 않게 처리한다 (PFQV-65).
- `AGENTS.md`의 명령어 표(`pnpm db:seed`)와 폴더 구조(`lib/seed/`, `lib/time/`)는 이미 적혀 있다. 실제로 만든 것과 다르면 고친다.

## 완료 기준

직접 실행해서 확인하고, 결과를 보고에 그대로 적는다.

| 확인 | 기준 |
| --- | --- |
| `pnpm lint` | 오류 0 |
| `pnpm typecheck` | 오류 0 |
| `pnpm test` | 전부 통과, 건너뛴 테스트 없음. 1–4단계의 테스트 포함 |
| `TZ=America/Los_Angeles pnpm test` | 전부 통과 |
| `pnpm build` | `DATABASE_URL`, `AUTH_SECRET` 없이 성공 |
| `pnpm db:generate` | 새 마이그레이션 파일이 생기지 않음 |
| `git status` | 깨끗함 |
| 경계 | `scripts/`와 `lib/seed/`가 `@/lib/db`를 직접 import하지 않음. `process.env`를 직접 읽지 않음 |
| 데이터 | 코드에 지점·공간·계정 데이터가 따로 적혀 있지 않고 세 JSON 파일에서만 옴 |

`pnpm db:seed`의 실제 실행은 DB가 없어 확인할 수 없으므로 "확인 못 함"으로 적고, 사람이 할 순서(`pnpm db:migrate` → `pnpm db:seed` → `/admin/login`)를 보고에 적는다.

## 막혔을 때

- 인증 인스턴스의 도우미로 일반 계정을 만들 수 없으면, 인증 테이블에 직접 쓰는 방법으로 바꾸지 말고 무엇이 안 되는지 알린다.
- 세 JSON 파일의 내용이 서로 맞지 않거나 스키마와 맞지 않으면, 파일을 고치지 말고 어느 항목인지 알린다.
- 문서끼리 다르면 `AGENTS.md`, `docs/spec/`, 이 지시서 순으로 우선한다. 다른 점은 보고에 적는다.
