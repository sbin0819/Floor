# Floor

공유오피스 멤버가 평면도에서 공간을 찾아 예약하고, 예약에 붙은 채팅과 영상 통화로 대화하는 서비스예요.

현재는 가입·로그인, 팀 가입, 개발용 시드, 시간·좌석 예약과 참석자 초대·알림, 운영자의 지점·층·공간 관리, 팀 채팅까지 구현했어요. Better Auth로 Google·GitHub·이메일 비밀번호 로그인, 이메일 인증과 비밀번호 재설정을 제공하고, 운영자 계정 생성 CLI도 있어요. 일반 회원은 팀을 만들거나 이메일 초대를 수락하거나 가입 요청을 승인받아 팀원이 될 수 있어요. `pnpm db:seed`로 가상 지점·공간·팀·계정·일정을 준비할 수 있어요. 팀 역할 변경·내보내기·탈퇴, 공유 초대 링크, 평면도 렌더러, 영상 통화와 실제 메일 서비스는 아직 없어요. 별도 API 서버나 배포는 만들지 않아요.

## 시작하기

Node 22 LTS(22.12 이상)와 pnpm 12.8.1이 필요해요. `.nvmrc`는 Node 22, `package.json`의 `packageManager`는 pnpm 12.8.1을 지정해요. Next.js 16.3.8과 React 19.2.8은 기존 버전을 유지해요.

```sh
pnpm install --frozen-lockfile
pnpm dev
```

[http://localhost:3000](http://localhost:3000)에 로그인하지 않고 들어가면 `/login`으로 안내해요. 세션 쿠키가 없는 공개 화면과 빌드·테스트·마이그레이션 생성은 실제 DB 없이 확인할 수 있어요. 실제 가입·로그인에는 아래의 [환경 변수와 Neon 준비](#환경-변수와-neon-준비)가 필요해요.

## 구조와 개발 규칙

회원 화면은 1280px 이상에서 72px 레일·248px 사이드바를, 768–1279px에서 레일과 메뉴 서랍을 써요. 모바일은 메뉴 서랍과 기존 아래 탭을 유지하고, 상단에 고정된 56px 위 줄에는 구역 이름과 알림 종 하나만 표시해요.

기능별 쓰기는 `features/*/actions.ts`에서 `createAction`으로 만들고, 첫 화면 데이터 읽기는 Server Component → `features/*/queries.ts` → DAL 순서로 처리해요. 읽기에는 Server Action을 쓰지 않아요. Route Handler는 캐시할 GET·외부 웹훅·Better Auth와 화면이 열린 동안 다시 읽는 참석자 검색(`/api/participants/search`)·알림(`/api/notifications`) GET에만 허용해요. 뒤의 두 GET은 `features/*/queries.ts`만 호출하고 그 함수가 세션을 확인하며, 응답은 `private, no-store`예요. 가입·로그인·로그아웃 등 인증 요청은 예외로 `/api/auth/[...all]`이 처리하며 Server Action 래퍼를 거치지 않아요.

업무 DB는 DAL에서만 읽고 써요. 인증 저장소는 Better Auth의 Drizzle 어댑터가 기존 `users`와 인증 테이블에 연결해요. ESLint는 `lib/db` import를 `lib/db`, `lib/dal`, `lib/auth/auth.ts`, `tests/db`, `drizzle.config.*`로 제한해요. 환경 변수는 `lib/env.ts`와 루트 설정 파일만 직접 읽을 수 있어요. 테스트에는 DAL의 마지막 DB 인자로 PGlite 클라이언트를 주입할 수 있어요.

Better Auth를 직접 부르는 곳은 `lib/auth/*`와 인증 Route Handler로 제한해요. 브라우저의 `authClient`는 `(auth)` 화면과 머리글의 로그아웃 버튼만 사용해요. 다른 코드는 아래 세션 가드를 사용해요.

역할 권한은 `can()`, 층·공간 접근은 `canAccessFloor()`와 `canAccess()`로 판정해요. 화면에서 버튼을 숨겨도 서버 판정은 반드시 수행해요. DB 스키마와 권한·평면도 규칙의 기준은 [명세 문서](docs/spec/)예요.

### Cache Components

`next.config.ts`에서 `cacheComponents: true`를 켜고 React Compiler는 비활성으로 둬요. 세션·쿠키·헤더·`params`·`searchParams`를 읽는 UI는 `<Suspense>` 아래의 Server Component에서 실행해요. 인증 화면의 제공자·메일 가능 여부도 `connection()` 뒤 요청 시점에 읽어요. 세션·권한·소속 조회에는 `use cache`, `use cache: private`, `use cache: remote` 어느 것도 붙이지 않아요.

레이아웃은 공통 틀과 `<Suspense>` 아래의 요청 단위 읽기를 제공하지만 접근을 막는 수단은 아니에요. 보호가 필요한 페이지와 조회·액션이 각각 직접 확인해요.

공유 레이아웃의 `<Suspense>`만으로는 페이지 간 이동을 처리할 수 없어요. 각 페이지도 동기 화면 틀 → `<Suspense>` → 비동기 내용 구조로 만들고, 세션 가드·조회·URL 매개변수 읽기를 안쪽에서 실행해요. 공유 레이아웃 안의 경계는 이동 시 페이지의 재렌더 범위보다 위에 있기 때문이에요. 빌드와 초기 페이지 요청뿐 아니라 개발 모드의 탐색 검사도 확인해요. 경고를 숨기기 위해 `instant = false`를 설정하거나 세션을 요청 사이에 캐시하지 않아요.

| 함수                       | 용도와 실패 동작                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| `getSession()`             | `{ userId, email, name }` 또는 `null`. 세션 쿠키가 없으면 인증 인스턴스·DB를 만들지 않음         |
| `requireSession()`         | queries·액션용. 세션이 없으면 `ActionError("UNAUTHENTICATED")`                                   |
| `requirePageSession(next)` | `(app)`의 모든 페이지용. 세션이 없으면 `/login?next=…`                                           |
| `requireOperatorPage()`    | `admin`의 모든 페이지용. 비로그인은 `/admin/login`, 비운영자는 `/admin/login?error=not_operator` |

홈·팀 전환·팀 상세·개인 초대·지점·층·내 예약·운영자 페이지가 각각 가드를 호출해요. `features/admin/queries.ts`, `features/teams/queries.ts`, `features/bookings/queries.ts`도 독립적으로 세션·소속·권한을 확인해요. `proxy.ts`는 쿠키 유무만 보고 일찍 안내하는 편의 기능이며 쿠키 유효성을 검증하지 않아요. 오래된 쿠키만으로 `/login`에서 내보내지 않고, 로그인·가입 페이지가 실제 세션을 확인해요. 인증·재설정 화면은 로그인한 상태로도 열려요.

로그인 뒤 목적지는 `safeNext()`를 통과한 같은 사이트의 경로만 사용해요. 외부 주소, 역슬래시·제어 문자, 인증 API, 로그인 화면으로 되돌아가는 목적지는 `/`로 바꿔요. 이메일 인증 후에는 목적지와 무관하게 `/login?verified=1`로 이동하며 자동 로그인하지 않아요. `<Suspense>` 안의 `redirect()`는 틀이 먼저 전송되면 HTTP 200으로 처리될 수 있어요.

새 Next.js 코드를 작성하기 전에는 설치된 버전의 `node_modules/next/dist/docs/`를 확인해요. 특히 `01-app/02-guides/authentication-with-cache-components.md`에 이 규칙의 배경이 있어요.

### 조회 속도와 로딩

`getSession()`과 DAL의 공통 읽기는 모듈 범위 React `cache()`로 서버 렌더 한 번 안에서만 공유해요. 키는 사용자·지점·층 ID 같은 원시 값이고 요청이 끝나면 버려져요. 테스트·트랜잭션이 DB를 주입하면 메모를 우회해요. `loadPermissionData()`는 권한 컨텍스트와 한도 설정을 함께 읽어 중복 조회를 줄여요. 요청 사이의 인증 캐시나 `use cache`는 쓰지 않아요.

접근 메타데이터와 허용 팀은 JOIN으로 읽고, 권한 판정이 끝난 공간만 이름·일정을 조회해요. 독립적인 읽기는 `Promise.all`로 묶고 층별 공간 수와 예약 방식별 사용량은 일괄 집계해요. `getSpaceDay(branchId, floorId, spaceId, date?)`는 주소의 부모 관계도 실제 행으로 확인해요.

모든 fallback은 화면 구조를 닮은 스켈레톤이에요. 가장 바깥의 `aria-busy`와 보이지 않는 상태 문구는 내용이 오면 사라지고, 모션 감소 설정에서는 반짝임이 멈춰요. 층 화면의 지점·층·날짜 줄은 지점 레이아웃에 남고, 공간 목록과 상세는 형제 Suspense에서 독립적으로 읽어요. 유효하지 않은 공간은 선택 없는 상자로 돌아가요.

주소만 바꾸는 링크는 `<a href>`를 유지해요. `useOptimistic`과 transition이 서버 응답 전에 선택 표시를 바꾸고 이동으로 바뀌는 영역에만 스켈레톤을 보여줘요. 공간 선택은 상세만, 날짜 변경은 목록과 선택된 상세만 바뀌어요. 층 변경·닫기는 상세를 즉시 비워요. 액션 뒤 `router.refresh()`는 이전 내용을 유지해요. 오류 화면의 다시 시도는 Next.js `retry()`로 서버 데이터를 다시 읽어요.

조회 예산은 네트워크 시간 대신 SQL 대기 의존성을 재요. `tests/db/query-meter.ts`는 한 타이머 턴에 들어온 문장을 모아 전부 끝난 뒤 결과를 함께 반환해요. 트랜잭션 내부 문장은 하나씩 세며 마이그레이션·시드·세션 확인은 측정에서 빼요. 대부분 2단계 이하, 지점을 먼저 고르는 홈 카드·예약 진입은 3단계 이하이고 한 단계는 6문장까지예요.

```sh
pnpm exec vitest run tests/db/query-meter.test.ts tests/db/query-budget.test.ts
```

최적화 전 실제 측정은 `tests/db/query-budget-baseline.json`에 남아 있어요. 단위·PGlite 검사는 실제 PostgreSQL 다중 연결 부하 검증이 아니에요. 개발용 Neon 브라우저 확인은 기존 계정 로그인·조회·화면 이동까지만 하고 예약·취소·설정 저장은 별도로 수동 확인해요.

| 초대 링크                         | 2 / 2   | 2 / 2      | 1, 1       |
| 운영 지점: 두 층                  | 6 / 10  | 2 / 6      | 4, 2       |
| 운영 층: 검색                     | 9 / 11  | 2 / 7      | 5, 2       |

층 여덟 개와 팀 소속 여덟 개를 더한 검사에서도 공간 상세·층 목록·운영 지점의 문장 수는 같았어요.

08에서 멤버 화면을 확장한 뒤의 추가·변경 조회예요. 기존 상세·내 예약·관리 조회 예산도 그대로 검사해요.

| ----------------------------------------- | --------------- | ---------- |
| 홈 머리말                                 | 1 / 1           | 1          |
| 다가오는 내 예약                          | 1 / 1           | 1          |

홈의 빈 공간과 지점 집계도 층 여덟 개·팀 소속 여덟 개를 늘려도 문장 수가 늘지 않아요. 목록의 일정은 시작·끝·종류만 전달하고, 접근할 수 없는 공간의 이름·일정이나 검색 대상 팀의 팀원 수는 읽지 않아요.

09의 운영자 홈 집계는 **2단계 / 2문장 (1, 1)**이에요. 담당 지점이 11개이고 층을 80개 더한 검사에서도 같아요. 기존 운영자 이름 목록과 단일 지점 바로 이동은 유지하고, 집계 SQL에도 담당자 조건을 다시 넣어 다른 지점의 이름·주소·개수를 읽지 않아요.

### 액션 래퍼 사용 예

아래는 DB 쓰기 없이 래퍼의 사용법을 확인하는 테스트용 예제예요. 두 번째 인자로 세션을 주입하는 것은 테스트에서만 사용하고, 실제 기능 액션은 기본 `getSession()`을 사용해요.

```ts
import { z } from "zod";
import { createAction } from "@/lib/actions/create-action";
import { can } from "@/lib/permissions/can";
import type { PermissionContext } from "@/lib/permissions/types";

const userId = crypto.randomUUID();
const context: PermissionContext = {
  userId,
  teams: [],
  staffBranchIds: [],
  roleSettings: {},
};

const action = createAction(
  {
    input: z.object({ title: z.string().trim().min(1) }),
    authorize: ({ session }) =>
      session.userId === context.userId && can(context, "booking.own", {}),
    handler: ({ session, input }) => ({
      title: input.title,
      requestedBy: session.userId,
    }),
  },
  {
    getSession: async () => ({
      userId,
      email: "member@example.com",
      name: "테스트 멤버",
    }),
  },
);

const result = await action({ title: "팀 회의" });
// { ok: true, data: { title: "팀 회의", requestedBy: userId } }
```

래퍼는 세션 → Zod 입력 검증 → `authorize` → `handler` 순서를 보장해요. `authorize`는 필수이며 권한 판정이 필요 없는 액션도 `authorize: "none"`을 명시해요. 비로그인 액션은 `auth: "public"`을 명시하고, 이때 `session`은 `Session | null`이에요.

실제 기능에서는 `loadPermissionContext(session, branchId)`로 서버에서 소속·권한을 읽고 `can()`과 `canAccess()`를 적용해요. `handler`의 DB 작업은 DAL로 구현하고 여러 쓰기는 `withTransaction()`으로 묶어요. 클라이언트가 보낸 사용자 id·역할·소유자는 신뢰하지 않아요. 액션을 내보내는 기능 파일에만 `"use server"`를 붙이고 래퍼 파일에는 붙이지 않아요.

결과는 `{ ok: true, data }` 또는 `{ ok: false, code, fieldErrors? }`예요. `ActionError`는 지정한 코드를 반환하고, Drizzle 오류의 `cause` 사슬에 있는 SQLSTATE `23P01`은 `BOOKING_CONFLICT`로 변환해요. `23505`는 제약 이름으로 팀 이름 중복(`TEAM_NAME_TAKEN`)과 대기 요청 중복(`ALREADY_REQUESTED`)을 구분해요. 나머지는 `INTERNAL`과 고정 서버 로그만 남겨요. 오류 객체·SQL·입력·토큰을 로그로 출력하지 않아요. 코드 목록은 [서버 명세](docs/spec/server.md)에 있어요.

## 환경 변수와 Neon 준비

| 변수                                       | 필요한 시점과 규칙                                                 | 기본값                  |
| ------------------------------------------ | ------------------------------------------------------------------ | ----------------------- |
| `DATABASE_URL`                             | 실제 DB·인증 접근, `db:migrate`, `admin:create`, `db:seed`         | 없음                    |
| `AUTH_SECRET`                              | 실제 인증·계정 생성·시드에 필수. 32바이트 이상의 무작위 값         | 없음                    |
| `SEED_ALLOW_HOST`                          | 원격 개발 DB의 시드 허용 호스트. URL의 호스트와 정확히 일치해야 함 | 없음                    |
| `NEXT_PUBLIC_APP_URL`                      | 앱과 인증 콜백의 기준 주소                                         | `http://localhost:3000` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | 둘 다 있을 때만 Google 로그인 활성화                               | 없음                    |
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | 둘 다 있을 때만 GitHub 로그인 활성화                               | 없음                    |
| `NODE_ENV`                                 | Next.js가 설정. `production`에서는 콘솔 메일 발송·시드 금지        | `development`           |

`parseEnv(source)`는 전달한 값만 검증하고, 앱에서는 `getEnv()`를 사용해요. 선택 값의 빈 문자열은 없는 것으로 취급해요. OAuth 설정은 한쪽만 있으면 오류예요. `AUTH_SECRET`이 있으면 UTF-8 기준 최소 32바이트를 검증하며, 없는 상태도 빌드·테스트를 위해 허용해요. DB와 인증 인스턴스는 첫 실제 사용 시 생성해요. 세션은 Better Auth의 DB 세션과 쿠키를 사용하며 만료 7일, 갱신 주기 1일이에요.

실제 DB 연결은 사람이 다음 순서로 진행해요.

1. Neon 프로젝트를 만들고 사용할 DB의 연결 문자열을 받아요.
2. 로컬 설정 파일이 아직 없다면 `.env.example`을 `.env.local`로 복사해요. 기존 파일은 덮어쓰지 않아요.
3. `DATABASE_URL`을 채우고 `openssl rand -base64 32`로 생성한 무작위 값을 `AUTH_SECRET`에 설정해요. 출력한 비밀 값을 저장소나 공유 로그에 남기지 않아요.
4. 아래 명령으로 대상 DB에 마이그레이션을 적용해요.

```sh
pnpm db:migrate
```

Drizzle 설정은 `db:migrate`를 실행할 때만 `.env.local`을 읽어요. 순서는 `0000_enable-btree-gist.sql` → `0001_initial-schema.sql` → `0002_bookings-exclusion.sql` → `0003_auth-foundation.sql` → `0004_team-join.sql` → `0005_booking-foundation.sql` → `0006_space-admin.sql` → `0007_space-photos.sql` → `0008_motionless_stature.sql` → `0009_true_spitfire.sql` → `0010_perfect_white_queen.sql` → `0011_charming_paladin.sql`이에요. `0003`은 인증 필드와 인증 테이블, `0004`는 팀 정보·초대 처리 상태·가입 요청, `0005`는 기본 지점과 취소 감사 필드, `0006`은 활성 공간 이름의 부분 유니크 인덱스, `0007`은 공간 사진과 지점 대표 사진을 추가해요. 예약 2차의 `0008`은 사용 인원과 범위 CHECK, `0009`는 예약 참석자, `0010`은 알림과 미리 알림 유니크 인덱스, `0011`은 nullable 예약 수정 시각을 추가해요. 기존 취소 행은 CHECK를 추가하기 전에 생성 시각을 취소 시각으로 채워요. 이미 적용한 파일과 기존 PK 이름은 유지해요. `btree_gist`와 예약 EXCLUDE 제약도 그대로 유지하며 애플리케이션의 사전 검사로 대신하지 않아요.

이어서 필요한 OAuth 앱을 등록하고, 아래 운영자 CLI로 운영 계정을 준비한 뒤 `pnpm dev`를 실행해요. 일반 회원은 `/signup`, 운영자는 `/admin/login`에서 시작해요. Neon은 PostgreSQL 저장소로 사용하며 별도의 Neon Auth 서비스는 연결하지 않아요. `.env*` 중 커밋하는 파일은 `.env.example`뿐이에요.

스키마를 바꿀 때는 `lib/db/schema`를 수정한 뒤 `pnpm db:generate`를 실행해요. 이미 커밋한 마이그레이션은 수정하지 않아요. 현재 스키마에서 다시 생성하면 새 파일이 없어야 해요. 실제 Neon 접속과 `db:migrate`는 로컬 테스트에 포함하지 않아요.

기존 개발 DB에 적용할 때는 먼저 활성 공간 이름 중복과 시드 고정 ID·고유값 충돌을 확인해요. 시드 대상에 다른 허용 팀이나 예약의 채팅 참조가 있으면 자동으로 정리하지 말고 멈춰요. 적용 전후에 기존 계정·비밀번호·소속과 시드 대상 밖 데이터를 비교하고, 시드 건수는 DB 전체가 아닌 시드 ID만 세어요. `.env.local`을 바꾸지 않으려면 확인한 정확한 호스트를 실행 환경의 `SEED_ALLOW_HOST`로 전달할 수 있어요. 기본 실행은 기존 인증 완료 계정의 비밀번호를 바꾸지 않아요.

### Google·GitHub OAuth 앱

Google은 [Google Cloud Console](https://console.cloud.google.com/)에서 웹 애플리케이션 OAuth 클라이언트를, GitHub는 [Developer settings](https://github.com/settings/developers)에서 OAuth App을 만들어요. 등록한 앱의 ID·Secret 쌍을 위 환경 변수에 넣고 서버를 다시 실행해요. 콜백 경로는 Better Auth의 [Google](https://better-auth.com/docs/authentication/google)·[GitHub](https://better-auth.com/docs/authentication/github) 안내를 따라요.

| 제공자 | 로컬에 등록할 콜백 주소                          | 다른 환경의 콜백 주소                            |
| ------ | ------------------------------------------------ | ------------------------------------------------ |
| Google | `http://localhost:3000/api/auth/callback/google` | `{NEXT_PUBLIC_APP_URL}/api/auth/callback/google` |
| GitHub | `http://localhost:3000/api/auth/callback/github` | `{NEXT_PUBLIC_APP_URL}/api/auth/callback/github` |

앱 주소·포트·프로토콜을 콜백 등록값과 일치시켜요. 설정이 완성된 제공자 버튼만 요청 시점에 보여주고 비밀 값은 클라이언트에 내려주지 않아요. 제공자가 이메일을 미인증으로 알려주면 로그인을 거절해요. 이미 있는 미인증 비밀번호 계정에는 소셜 수단을 연결하지 않아요. 인증된 비밀번호 계정에 소셜 수단이 처음 연결되면 기존 비밀번호와 세션을 삭제하고 안내 메일을 보내요. 비밀번호 로그인도 쓰려면 다시 재설정해야 해요.

회원용 인증 화면 다섯 곳은 1024px 이상에서 정적인 소개와 400px 양식 카드 두 칸으로 보여줘요. 좁은 화면과 운영자 로그인에는 카드만 남아요. 소개는 바로 보이고 세션·제공자·주소 쿼리를 읽는 양식은 카드 모양 스켈레톤 뒤에서 열려요. 비밀번호 보기·숨기기는 값과 자동 완성 설정을 유지하며 키보드로 조작할 수 있어요. 인증 안내에는 메일함 열기 → 링크 누르기 → 돌아와서 로그인하기 순서가 있고, 개발 환경의 콘솔 메일 안내는 서버에서 판단해요. 인증·오류 문구·안전한 `next` 규칙은 바꾸지 않았어요.

### 개발 메일과 production 제한

외부 메일 서비스는 아직 없어요. `pnpm dev`에서 가입·인증 재발송·비밀번호 재설정을 하면 받는 사람, 제목, 본문을 **개발 서버 터미널**에 출력해요. 브라우저 콘솔이나 실제 받은 편지함이 아니라 이 서버 로그에서 링크를 찾아 열어요. 인증 링크를 열면 `/login?verified=1`로 돌아오고 직접 로그인해야 해요. 재설정을 마치면 이전 비밀번호와 세션은 사용할 수 없어요.

`NODE_ENV=production`의 콘솔 구현은 링크를 출력하지 않고 오류를 내요. 따라서 `pnpm build && pnpm start`에서도 `/signup`, `/forgot-password`, `/verify-email`의 이메일 양식 대신 다음 안내를 표시해요. 켜진 소셜 버튼은 유지해요.

> 지금은 이메일로 가입하거나 재설정할 수 없어요. Google이나 GitHub로 계속해 주세요

메일을 발송하지 못해도 Better Auth가 성공 모양으로 응답할 수 있으므로 이 안내를 숨기면 안 돼요. 메일 서비스 연결 전에는 소셜 로그인과 이미 인증된 계정(운영자 CLI 계정 포함)의 비밀번호 로그인을 사용할 수 있어요. 제공자를 하나도 설정하지 않으면 소셜 버튼도 없어요. 이메일 가입·재설정의 실제 운영 사용은 메일 서비스 연결 후 확인해요.

요청 제한은 Better Auth 기본값을 유지해요. production에서 메모리 저장소를 사용하므로 여러 서버 간 제한은 공유되지 않으며 배포 전 다시 정해야 해요. 화면의 인증 재발송 60초 대기는 편의 기능일 뿐 서버 제한을 대신하지 않아요.

### 이번 범위에서 비활성화한 인증 경로

## 운영자 계정 만들기

공개 가입으로는 운영자가 될 수 없어요. 마이그레이션과 `DATABASE_URL`·`AUTH_SECRET` 설정을 먼저 마친 뒤, 저장소 루트에서 실행해요.

```sh
pnpm admin:create --help
pnpm admin:create --email ops@example.com --name "가상 운영자" --branch "가상 지점" --create-branch
```

두 번째 명령은 지점이 없으면 만들고 새 계정을 이메일 인증이 끝난 상태로 등록해요. 비밀번호를 생략하면 안전한 무작위 값을 만들어 표준 출력에 한 번만 보여줘요. 값을 안전한 곳에 보관하고 공유 로그에 남기지 않아요.

| 옵션               | 동작                                                                      |
| ------------------ | ------------------------------------------------------------------------- |
| `--email`          | 필수. 앞뒤 공백을 제거하고 소문자로 바꾼 유효한 이메일                    |
| `--name`           | 새 계정에서 필수. 앞뒤 공백을 뺀 1–50자. 기존 이름은 바꾸지 않음          |
| `--branch`         | 필수 지점 이름. 앞뒤 공백을 제거하며 동일 이름이 둘 이상이면 오류         |
| `--create-branch`  | 지점이 없으면 기본 시간대로 생성. 생략하면 없는 지점은 오류               |
| `--password`       | 8–128자. 새 계정 또는 `--reset-password`에서만 설정. 생략하면 무작위 생성 |
| `--reset-password` | 기존 비밀번호 교체·모든 세션 삭제·이메일 인증 처리를 한 트랜잭션으로 수행 |
| `--help`           | 환경 변수나 DB 연결 없이 사용법 출력                                      |

이미 인증된 계정에 다른 지점을 추가하려면 이름과 비밀번호를 생략해요. 이미 같은 지점의 운영자여도 성공하며 기존 비밀번호를 유지해요.

```sh
pnpm admin:create --email ops@example.com --branch "다른 가상 지점" --create-branch
```

미인증 기존 계정은 `--reset-password` 없이는 실패해요. 기존 계정의 비밀번호를 재발급할 때도 같은 옵션을 명시해요.

```sh
pnpm admin:create --email ops@example.com --branch "가상 지점" --reset-password
```

비밀번호를 직접 정하려면 `--password "직접 정한 8–128자 비밀번호"`를 더할 수 있지만 셸 기록에 남을 수 있어요. 기존 계정에는 `--password`만 전달해도 비밀번호가 바뀌지 않아요. Google·GitHub가 연결된 계정이면 그 로그인 수단으로도 운영자 화면에 들어올 수 있다는 경고를 출력해요.

명령은 `node --conditions=react-server --import=tsx --env-file-if-exists=.env.local scripts/admin-create.ts`를 실행해요. `react-server` 조건은 Next.js 밖에서도 `server-only` 경계를 유지하기 위한 것이고, `tsx`는 TypeScript와 경로 별칭을 처리해요. Node가 `.env.local`을 있으면 읽고, 실제 환경 검증은 `lib/env.ts`가 해요. 필수 값이 없거나 입력·DB 작업이 실패하면 비밀 값 없이 안내하고 실패 코드로 끝나요.

완료 후 `/admin/login`에서 이메일·비밀번호로 로그인해 `/admin`의 운영 지점 목록을 확인해요. `/admin/login`은 안내용 입구이고 실제 경계는 페이지·queries의 서버 검사예요. 운영자가 아닌 로그인 상태에서는 자동 로그아웃하지 않고 홈으로 가거나 명시적으로 다른 계정으로 로그인할 수 있어요.

## 개발용 목 데이터와 계정

시드는 개발 전용 DB에서만 사용해요. 저장소에 공개된 비밀번호의 운영자 계정을 만들기 때문에 **배포한 사이트가 사용하는 DB에는 시드를 넣지 마세요.** `NODE_ENV=production`이면 DB에 접속하기 전에 거절해요. 개발 모드로 실행하더라도 운영 DB를 가리키도록 설정하면 안전하지 않아요.

`DATABASE_URL`과 `AUTH_SECRET`을 먼저 준비해요. `localhost`와 `127.0.0.1`은 별도의 호스트 허용 값이 필요 없어요. Neon 등 원격 개발 DB는 `.env.local`의 `SEED_ALLOW_HOST`에 `DATABASE_URL`의 **호스트 이름만** 정확히 적어요. 프로토콜·사용자·비밀번호·포트·경로를 넣거나 연결 문자열 전체를 복사하면 안 돼요. 허용하지 않은 호스트로 실행하면 필요한 호스트 이름을 안내하고 연결하지 않아요.

저장소 루트에서 아래 순서로 실행해요. `--help`는 환경 설정이나 DB 연결 없이 확인할 수 있어요.

```sh
pnpm db:seed --help
pnpm db:migrate
pnpm db:seed
pnpm dev
```

이어서 `/admin/login`에서 아래 운영자 계정으로 로그인하고 `/admin`의 강남점·성수점·홍대점·여의도점·판교점 목록을 확인해요. 나머지 계정은 `/login`을 사용해요. 모든 시드 계정은 이메일 인증이 끝난 상태이고, 계정 생성은 Better Auth의 공용 계정 준비 도우미를 거쳐요. 인증 메일이나 로그인 세션을 만들지 않아요.

| 이메일                    | 비밀번호     | 이름·역할                       |
| ------------------------- | ------------ | ------------------------------- |
| `admin@floor.com`         | `admin1234!` | 관리자 · 다섯 지점 운영자       |
| `member@floor.com`        | `floor1234!` | 김하은 · 팀 없는 일반 회원      |
| `design.admin@floor.com`  | `floor1234!` | 박지훈 · 디자인팀 관리자        |
| `design.member@floor.com` | `floor1234!` | 이서연 · 디자인팀 회원          |
| `growth.admin@floor.com`  | `floor1234!` | 최민준 · 그로스팀 관리자        |
| `both@floor.com`          | `floor1234!` | 정유나 · 디자인팀·그로스팀 회원 |

기본 데이터는 [seed.json](docs/spec/examples/seed.json), [7층 공간](docs/spec/examples/gangnam-7f.spaces.json), [7층 평면도](docs/spec/examples/gangnam-7f.plan.json)에서 읽고, [예약 2차 자료](docs/spec/examples/seed-bookings-2.json)와 [사진 자료](docs/spec/examples/seed-photos.json)를 함께 검증해요. 비어 있는 개발 DB 전체 시드는 지점 5곳, 층 11개, 공간 71개(7층 33개 포함), 팀 2개, 계정 6개, 팀 소속 5개, 운영자 소속 5개, 허용 팀 2개, 게시된 평면도 1개, 예약 30개(확정 26개·취소 4개), 점검 5개, 참석자 5행이에요. 공간 사진 65행과 지점 대표 사진 5개도 있어요. 미리 알림 건수는 실행 시점 뒤에 남아 있는 예약 시각에 따라 달라요. 코드에 별도의 목 데이터를 중복해서 적지 않아요.

### 기존 DB에 새 지점만 추가하기

기존 두 지점이 있는 개발 DB에는 전체 시드를 다시 실행하지 않고 아래처럼 범위를 지정해요. 호스트는 실행 환경의 `SEED_ALLOW_HOST`로 전달해도 돼요.

```sh
pnpm db:seed --branches 30f94644-2de6-54db-93bd-0a1f5ad55cdd,34db02c8-7a13-5ca1-aae8-d7bcb74189f4,bfc43c7c-c340-5a15-99ea-ccd4f4fca60e
```

- 순서대로 홍대점(2·3층), 여의도점(10·11층), 판교점(4·5층)이에요. 지점마다 공개 공간 8개 중 6개를 예약할 수 있고, 예시 예약 4개와 점검 1개가 있어요. 기존 사진 파일을 재사용해요.
- `--branches`는 **추가 전용**이에요. 없는 지점 묶음만 한 트랜잭션으로 넣고, 이미 완전히 추가된 지점은 그대로 건너뛰어요. 다시 실행해도 기존 예약 날짜·취소 상태·운영 설정·사진을 되돌리지 않아요.
- 필요한 기존 계정은 이메일 인증을 마친 상태여야 해요. 계정·암호·세션·팀·팀 소속·기본 지점을 변경하지 않고, 새 지점의 운영자 소속만 추가해요.
- 알 수 없는 ID·중복·빈 범위와 `--reset-passwords` 병용은 거절해요. 고정 ID의 부모 관계가 다르거나 묶음이 불완전하면 자동 복구하지 않고 중단해요. 신규 평면도를 포함한 지점 추가는 지원하지 않아요.
- 아래의 전체 시드 재실행 규칙은 **범위 옵션을 모두 생략했을 때만** 적용돼요. 실제 DB 전체 건수와 이번에 추가한 건수를 구분해서 확인해요.

### 기존 DB에 예약 2차만 추가하기

마이그레이션과 기존 데이터 검사를 마친 개발 DB에서 `pnpm db:seed --booking-round2`를 사용해요. `--branches`나 `--reset-passwords`와 함께 쓰지 않아요. 기존 계정과 지점·소속·예약 날짜는 유지하고 지정된 사용 인원 6개, 참석자 5행, 좌석 예약 9개, 점검 1개와 미래 미리 알림만 한 트랜잭션으로 넣어요. 필요한 기존 계정·예약이 없거나 충돌·부분 적용이 있으면 자동 복구 없이 멈춰요.

커밋 후 Git에서 제외한 `.floor-local/seed-receipts/`에 비밀 값 없는 완료 표식을 저장해요. 표식과 불변 데이터가 일치하는 재실행은 조회만 하고, 취소·참석 취소·읽음을 되돌리지 않아요. 표식이 없거나 손상된 경우 임의로 새로 만들거나 전체 시드로 복구하지 마세요. DB 적용 뒤 표식 저장이 실패했으면 자동으로 재시도하지 말고 상태를 확인해요. 이 모드는 계정을 생성하지 않아 `AUTH_SECRET`이 필요하지 않지만 정확한 `SEED_ALLOW_HOST` 검사는 그대로 적용돼요.

### 다시 실행할 때

- 고정 시드 ID의 지점·층·공간·팀은 원본 값으로 돌아가요. 시드 공간은 보관도 풀리고, 시드 대상 층·공간의 허용 팀은 원본 목록으로 맞춰져요. 이 대상에 따로 더했던 허용 팀도 제거되므로 주의해요.
- 시드 팀 소속의 역할·직함은 맞추지만, 목록 밖의 소속과 운영자 관계는 지우지 않아요. 시드에 없는 계정과 다른 데이터도 유지해요.
- 시드 평면도 ID가 이미 있으면 문서는 건드리지 않아요. 해당 층에 다른 게시된 평면도가 있으면 새 시드 평면도를 넣지 않고 층의 게시 포인터도 보존해요.
- 시드 ID의 예약·점검만 지웠다가 새 기준일에 넣어요. 다른 사람의 확정 예약과 겹치는 시드 예약은 건너뛰고 건수를 알려줘요. 취소된 시드 예약은 그대로 넣어요.
- 기존 이메일 인증 완료 계정은 이름·비밀번호를 유지해요. 미인증 계정이 같은 이메일을 차지하고 있으면 전체 시드를 거절해요. 다른 ID의 행이 팀 이름·층 번호 같은 고유 값을 이미 쓰거나 중간에 실패해도 한 트랜잭션 전체가 되돌아가요.

기존 시드 계정의 비밀번호를 표의 값으로 되돌릴 때만 다음 옵션을 사용해요. 시드 계정 6개의 비밀번호를 교체하고 이메일을 인증된 상태로 바꾸며 기존 세션도 모두 끊어요. 시드 목록 밖의 계정에는 적용하지 않아요.

```sh
pnpm db:seed --reset-passwords
```

CLI는 대상 호스트 이름, 처리 건수, 건너뛴 예약 수와 계정 이메일만 출력해요. 비밀번호·해시·연결 문자열은 출력하지 않아요. 실행은 운영자 CLI와 같은 `--conditions=react-server --import=tsx --env-file-if-exists=.env.local` 방식이고 새 패키지는 추가하지 않았어요.

시드 이메일은 실제 수신용으로 관리하는 주소가 아니에요. 실제 메일 서비스를 연결하기 전에 시드 계정에 메일이 나가지 않도록 차단해야 해요(PFQV-65).

### 지점 시간대와 운영일

`lib/time`은 `Intl`로 지점의 IANA 시간대를 명시해 계산해요. 서버·브라우저의 시간대에 기대지 않고, 현재 시각은 실행 함수에 주입해요. `24:00`은 다음 날 자정이고, 서머타임으로 없는 현지 시각은 그 뒤의 첫 시각, 두 번 있는 현지 시각은 앞의 시각으로 정해요.

운영 시간은 30분 단위이고 시작보다 끝이 늦어야 해요. 요일 값이 `null`이면 휴무이고, 요일 키가 없거나 저장된 형식이 잘못되었으면 기본 `09:00–22:00`으로 읽어요. 매일 휴무인 설정에서는 운영일을 계산할 수 없다고 알려요.

시드 예약의 기준일은 지점 시간대의 오늘이며, 휴무면 다음 운영일이에요. `dayOffset`은 달력 날짜가 아니라 운영일 수예요. 예를 들어 강남점에서 토요일에 실행하면 `dayOffset: 1`은 일요일을 건너뛴 월요일이에요. 시드는 예약 화면의 한도를 실행하지 않고 검증된 JSON 일정을 그대로 넣어요.

## 공간 찾기와 예약

홈은 머리말·다음 예약·지금 빈 공간 4곳·자주 쓰는 공간·이번 주 예약·개인 한도·내 팀을 각자의 조회와 Suspense로 보여줘요. 기존 다가오는 예약 3건 조회 계약은 유지하고 화면에는 첫 예약과 다음 한 건만 써요. 홈의 지점은 저장한 기본 지점, 이름순으로 본 팀의 주 이용 지점 순으로 고르고 머리말과 빈 공간 카드에 같은 지점을 써요. 둘 다 없으면 지점 고르기를 안내해요. 지점이 없는 홈 날짜는 서울 시간대예요.

| 주소                                                                                      | 화면                                                                                                      |
| ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `/booking?date=YYYY-MM-DD`                                                                | 선택 날짜를 유지해 홈이 쓰는 지점의 접근 가능한 첫 층으로 바로 이동                                       |
| `/branches`                                                                               | 지점 카드 링크·운영 상태·접근 가능한 층과 빈 공간 수, 별도의 기본 지점 버튼                               |
| `/branches/[branchId]`                                                                    | 접근 가능한 첫 층으로 이동, 없으면 안내                                                                   |
| `/branches/[branchId]/floors/[floorId]?date=YYYY-MM-DD&space=UUID&detail=1&view=timeline` | 층·날짜·목록/시간표, 공간 상세와 예약 양식 (`view=list`도 가능). `detail=1`은 선택한 공간의 상세를 열어요 |
| `/bookings`, `/bookings?tab=past`                                                         | 날짜별 다가오는 예약과 지난 예약, 상대 시간·취소 확인                                                     |
| `/bookings?view=calendar&month=YYYY-MM&day=YYYY-MM-DD`                                    | 내 확정 예약 월 달력과 선택 날짜의 예약·취소·새 예약 진입                                                 |

각 페이지 안의 Suspense 아래에서 `requirePageSession()`을 직접 부르고 모든 공개 조회도 독립적으로 세션과 접근을 확인해요. `/booking`은 지점이 없으면 목록으로, 층이 없으면 해당 지점 안내로 보내고 중간 지점 이동을 거치지 않아요. 날짜는 지점 현지 날짜의 오늘부터 60일 뒤까지이며 잘못된 날짜는 오늘로 처리해요. 다른 층의 공간이나 접근할 수 없는 공간은 선택하지 않아요. 공간 이름·정원·편의 시설·일정을 볼 수 없는 사람에게는 공간 ID와 종류만 보내고, 다른 사람의 예약 제목은 본인·그 팀원·그 지점 운영자에게만 보내요.

지점 카드는 대표 사진·접근 가능한 층 수·예약 가능한 공간 수·운영 중 빈 공간 수·요일별 운영 시간을 보여줘요. 최대 1040px, 1024px 이상 두 열이며 지점 이름 링크 하나의 클릭 영역만 카드 전체로 확장해요. 기본 지점 버튼은 링크와 분리돼요. 지점 카드 이동은 쓰기를 하지 않아요. 기본 지점은 **기본 지점으로 설정** 버튼, 또는 기본 지점이 비어 있는 사람의 첫 예약 성공 때만 저장해요. 첫 예약의 조건부 `UPDATE ... WHERE default_branch_id IS NULL`은 예약과 같은 트랜잭션이며 기존 값은 유지하고 실패하면 함께 롤백해요.

내 예약 달력은 6달 전부터 오늘+60일이 속한 달까지 이동해요. 기존 목록의 30일·50건 제한을 재사용하지 않고 월 전체 본인 확정 예약을 읽어 예약 지점의 현지 시작일로 분류해요. 같은 달의 날짜 링크는 History API로 패널만 바로 바꾸고, 월 이동은 서버 조회 후 달력·패널만 교체해요. 취소 후 새로고침은 기존 화면을 유지해요. 1024px 이상은 340px 선택 패널을 옆에 두고, 768px 미만은 44px 날짜 칸과 최대 세 개 점을 써요. 쉬는 날은 달력에 표시하지 않아요. `/booking`의 선택 날짜도 로그인 복귀 주소에 보존하며, 대상 지점의 오늘부터 60일 안인 날짜만 층으로 전달해요.

홈의 이번 주는 홈 지점 시간대의 오늘부터 7일이며 예약은 각 예약 지점의 현지 날짜 줄에 들어가요. 자주 쓰는 공간은 본인이 최근 30일 이후에 시작하는 확정 예약(미래 포함)을 많이 만든 순서예요. 현재 접근·예약 가능·보관 여부를 확인한 뒤 상위 세 곳의 이름과 사진을 읽고, 카드마다 해당 지점의 오늘 날짜로 이동해요. 빈 결과는 카드를 숨겨요.

층 화면은 지점·층·날짜 도구 줄과 목록/시간표, 선택한 공간으로 나뉘어요. 달력 버튼에서 오늘부터 60일까지 바로 고르고, 지점 현지 날짜의 **본인이 만든 확정 예약**에만 점을 표시해요. 보기는 URL `view` → `floor_view` 쿠키 → 화면 폭 순서예요. 미정이면 두 보기를 서버에서 그리고 CSS로 하나만 보여줘요. 1024px 이상은 시간표, 그보다 좁으면 목록이 기본이에요. 보기 링크는 Native History API로 주소만 바꿔 서버 재조회를 하지 않고, 1년·Path=/·SameSite=Lax 쿠키로 기억해요. 날짜·층·공간과 수정 키 클릭·뒤로 가기는 유지해요.

시간표는 30분 칸과 고정 공간 열로 구성돼요. 표 안에서만 가로로 스크롤하고, Tab 한 번과 방향키·Home·End로 이동해요. 표 칸은 넓은 화면 34px, 좁은 화면 44px이며 넓은 화면의 전역 클릭 영역 확대 예외를 적용해요. 가용 시간 띠와 시간표의 DTO에는 시작·끝·종류만 있어요. 겹친 점검과 예약은 별도 레인으로 보이고 둘 중 하나라도 있는 칸은 선택하지 못해요. 구간 위치와 길이는 실제 timestamp로 계산해 DST가 바뀌는 날에도 맞아요. 영업 전·후에는 “비어 있음”을 표시하지 않아요. 휴무일에는 안내 하나와 다음 영업일 링크만 보이고, URL에 공간이 있어도 상세를 열지 않아요. 60일 안에 운영일이 없으면 지점 변경을 안내해요.

시간표의 공간 칸을 누르면 `space`와 `detail=1`을 주소에 담아 공간 상세를 열어요. 1024px 이상 시간표에서는 오른쪽 420px 시트이고, 빈 시간 칸을 누르면 기존처럼 화면 아래 16px의 예약 줄이에요. 넓은 목록은 420px 패널, 좁은 화면은 85dvh 높이의 아래 시트로 같은 상세 내용을 한 번만 그려요. 오른쪽 시트를 닫으면 `detail`만 제거해 예약 줄로 돌아가고 포커스는 공간 칸으로 복귀해요. 목록 패널과 아래 시트의 닫기는 공간 선택도 제거해요.

선택 구간과 예약 제목·방식은 지점·층·날짜·공간 범위의 공유 상태예요. 보기나 상세만 바꾸면 유지하고 공간·층·날짜 변경 또는 공간 선택 해제 때 비워요. 예약 성공은 구간과 제목만 비우고 방식은 유지하며, 오른쪽 시트는 닫지 않아요. 늦은 성공 응답은 다른 공간의 입력을 지우지 않아요.

시트 컨테이너는 상세 조회의 Suspense 밖에 유지하고 안의 스켈레톤만 본문으로 교체해요. 한 번 호출한 `getSpaceDay`의 Promise를 검증 신호와 본문이 공유해요. 검증 신호는 닫힌 시트 밖에서 처리하므로 직접 주소로 들어와도 열 수 있고, 사용자가 먼저 닫거나 다른 공간을 골랐다면 오래된 응답이 다시 열지 못해요. 응답을 기다리는 선택과 서버가 확인한 선택을 구분하며, 접근할 수 없는 공간은 확인 후 닫아요.

현재 시각은 서버가 준 `now`에 경과 시간을 더한 지점별 표시 시계로 분마다 갱신해요. 머리글의 영업 상태와 시간표·상세의 시각선에만 쓰며 API 요청을 추가하지 않아요. 날짜 정규화와 예약 양식의 기준 시각은 서버 응답 값으로 유지하므로 자정을 넘겨도 선택 날짜나 입력이 저절로 바뀌지 않아요. 시각선은 **오늘의 운영 시간 안에서만** 보여요. 예를 들어 08:29에는 강남점(08–22시)에는 선이 있고 성수점(09–21시)에는 없으며, 성수점에는 “현재 08:29 · 09:00에 열어요”를 표시해요. 마감 뒤에는 “오늘 영업이 끝났어요”로 안내해요. 시각 배지는 눈금과 분리하고 가장자리에서도 보이며, “현재 시간으로 이동”을 누를 때만 현재 위치로 다시 스크롤해요.

목록 상세는 사진(160px, 높이 760px 미만에서는 120px)·정보·최소 280px 하루 일정·접힌 예약 양식이에요. 일정이 남는 높이를 쓰고 평소에는 일정만 스크롤해요. 아주 낮은 창에서는 바깥 스크롤을 허용해 내용을 자르지 않아요. 구간을 고른 뒤 “예약 내용 바꾸기”로 입력을 펼치고, 숨겨진 필드 오류도 자동으로 펼쳐요. 상세 빈 칸은 넓은 화면 28px, 시트에서 44px예요. 닫기는 즉시 반영하고 `replace`로 공간 선택을 없애며 현재 보이는 줄·칸으로 포커스를 돌려줘요. 늦은 이전 예약 응답은 새 공간의 선택이나 상세를 지우지 않아요.

예약은 지점 운영 시간 안에서 30분 단위, 같은 현지 날짜에 해요. 다음 날 `00:00`은 당일 `24:00` 종료로 허용하며 지금 진행 중인 칸의 시작부터 예약할 수 있어요. 날짜 계산은 지점 IANA 시간대를 명시하고 서머타임도 반영해요. `start`·`end`는 오프셋이 있는 ISO 시각만 받아요.

개인 예약에는 사용자 한도(해당 지점 운영자는 운영자 한도), 팀 예약에는 팀 회원 한도를 적용해요. 지점별 설정의 누락된 키는 기본값, `null`은 무제한이에요. 팀 한도는 같은 지점·현지 날짜의 팀원 전체 예약 시간을 합쳐요. 전용 공간은 허용된 소속 팀 이름으로만 예약하며, 해당 지점 운영자는 개인 예약이 가능해요. 한도 오류는 건당 시간·예약 가능 날짜·하루 시간 순서로 판정해요.

서버는 층 → 공간 → 사용자 → 팀 순서로 잠근 뒤 접근과 예약 가능 여부를 다시 읽어요. 개인 한도는 사용자 행, 팀 한도는 팀 행의 배타 잠금으로 보호해요. 점검을 확인한 뒤 예약을 넣고, 겹침은 DB EXCLUDE 제약의 `23P01`만 `BOOKING_CONFLICT`로 처리해요. 일정 이벤트는 커밋 뒤 발행하며 발행 실패가 저장 성공을 취소하지 않아요.

본인은 권한 설정과 관계없이 끝나지 않은 예약을 취소할 수 있어요. 팀 관리자와 해당 지점 운영자는 각 취소 권한도 필요해요. 취소 시각·취소자를 남기고 조건부 UPDATE로 중복 취소를 막아요. 취소자의 사용자 행도 UPDATE 전에 KEY SHARE로 잠가 FK 검사가 생성의 사용자 잠금과 역순이 되지 않게 해요. 취소된 예약은 하루 한도 합계에서 빠져요. 지난 예약은 각 지점 현지 날짜의 30일 전 자정 이후에 시작한 것 중 최대 50개예요.

양식은 예약·점검·지난 칸을 선택지에서 제외하고, 공통 mutation 잠금으로 중복 제출을 막아요. 성공 및 예약 충돌·점검 오류 뒤에는 서버 일정을 새로 읽고 낙관적으로 예약을 추가하지 않아요. 평면도 렌더러·실시간 구독은 구현하지 않았어요.

수동 확인은 마이그레이션 → 시드 → 김하은 로그인 → 강남점 7층 회의실 C 예약 → 내 예약에서 취소 → 이서연으로 8층 예약 순서예요. PGlite 검사는 실제 PostgreSQL 다중 연결의 동시 부하나 교착 상태 검증을 대신하지 않아요.

## 팀 회원으로 전환

`/teams`에 받은 초대·내 팀·보낸 가입 요청을 모아요. 내 팀의 팀원 수와 주 이용 지점은 소속 회원에게만 보여요. 요청은 대기 중인 것과 최근 30일 안에 거절된 최신 것만 보이고, 더 새로운 요청이나 소속이 있으면 지난 거절은 제외해요.

`/teams/start`는 고르기, `?mode=create`의 만들기, `?mode=join&q=...`의 검색으로 나뉘어요. 뒤로 가기와 링크 공유를 유지하면서 고른 단계의 제목이 즉시 바뀌어요. 검색은 NFC·공백 정규화 후 2–40자이며 이름과 주 이용 지점만 최대 10개 보여줘요. 검색 결과에는 팀원 수가 없고 이미 팀원·받은 초대·요청 보냄 상태를 구분해요. `%`, `_`, `\`는 검색 연산자가 아닌 문자로 취급해요.

- 새 팀을 만들면 생성자가 관리자가 돼요. 주 이용 지점은 지점이 있을 때 필수이고 권한 범위를 바꾸지 않아요. 관리자 팀은 회원당 최대 5개예요.
- 가입 요청은 회원당 대기 10개까지 보낼 수 있어요. 본인은 취소하고 대상 팀 관리자는 승인·거절할 수 있어요.
- 관리자는 `/teams/[teamId]`에서 이메일 초대를 만들거나 취소해요. 7일짜리 개인 초대이며, 팀당 미처리 50개까지예요. 만료됐지만 미처리인 초대도 한도와 관리자 목록에 포함해요. 같은 이메일로 다시 초대하면 이전 초대를 취소하고 새로 만들어요.
- 수신자는 받은 초대 목록이나 `/invite/[token]`에서 수락·거절해요. 인증된 이메일이 일치해야 해요. 다른 수신자·만료·처리 완료·잘못된 토큰은 모두 같은 안내를 보여줘요.

팀원이 아닌 사람에게 팀 상세는 존재하지 않는 팀과 동일하게 처리해요. 일반 팀원 조회는 관리자 연락처·보낸 초대·가입 요청을 읽지 않아요. 관리자 응답에도 초대 토큰은 포함하지 않아요. 승인과 수락은 기존 관리자 역할을 보존하고, 같은 팀의 대기 요청·초대를 한 트랜잭션에서 함께 정리해요.

초대 메일은 DB 커밋 뒤 보내요. 개발 모드에서는 기존 콘솔 메일로 확인하고, 메일을 보낼 수 없는 환경에서도 초대 등록은 허용해요. 발송 실패가 초대를 취소하지 않으며, 수신자는 로그인 후 받은 초대 목록에서 확인할 수 있어요. 화면은 등록 성공만 안내하고 메일 전송 성공을 단정하지 않아요. 요청 실패 로그에는 메일 본문·주소·초대 토큰을 넣지 않아요.

화면 쓰기는 TanStack Query mutation으로 실행하며 공통 실행 잠금과 동일 scope로 중복·병렬 제출을 막아요. 성공 뒤 서버 목록을 새로 읽고 멤버십을 낙관적으로 변경하지 않아요. 관련 사용자 UUID 오름차순 → 팀 행 → 조건부 상태 변경 순서로 잠그고, 한도 초과나 중간 실패는 전체 트랜잭션을 되돌려요.

이전 지시서의 마이그레이션이 아직 없다면 먼저 적용한 다음, 서로 다른 인증된 계정 두 개로 **팀 생성 → 초대 → 수락 → 다른 팀 가입 요청 → 승인**을 확인해요. 07–09 화면 개선 자체에는 새 마이그레이션이나 시드가 없어요. 자동 검사는 PGlite이며, 개발용 Neon의 브라우저 확인은 로그인·조회·이동까지만 해요. 쓰기와 실제 메일 발송은 별도의 수동 확인 대상이에요.

## 운영자의 지점·층·공간 관리

| 주소                                          | 할 수 있는 일                                      |
| --------------------------------------------- | -------------------------------------------------- |
| `/admin`                                      | 운영 지점 선택. 소속 지점이 하나면 바로 이동       |
| `/admin/branches/[branchId]`                  | 지점 이름·주소·요일별 운영 시간 수정, 층 목록·추가 |
| `/admin/branches/[branchId]/floors/[floorId]` | 층 정보·이용 대상, 공간 추가·수정·보관·복원        |

각 페이지는 `requireOperatorPage()`를 직접 부르고, 조회와 액션도 실제 층·공간 행의 지점으로 운영자 소속을 확인해요. 다른 지점의 데이터는 없는 데이터와 같은 응답이에요. 지점·층·공간 수정은 `space.manage`, 이용 대상 변경은 `plan.edit` 권한이 필요해요. 권한이 없는 화면 구역은 읽기 전용으로 남겨요. 모든 요청 정보는 페이지 내부 Suspense 아래에서 읽으며 캐시하지 않아요.

운영자 홈의 카드에는 담당 지점의 주소·오늘 운영 상태·층 수·보관되지 않은 비좌석 공간 수가 보여요. 경로 표시는 각 화면이 이미 읽은 지점·층 이름을 사용해요. 왼쪽 메뉴의 로그아웃은 아래에 남고, 1024px 미만에서는 메뉴가 위로 올라가요.

지점 화면은 지점 정보·요일별 운영 시간·층 표로 나눠요. 월요일 시간을 평일 전체에 적용하면 화–금의 입력만 바뀌고, 저장 버튼을 눌러야 기존 `updateBranch`로 일곱 요일을 함께 저장해요. 지점 이름·주소의 기존 수정 기능은 유지하고 시간대만 읽기 전용이에요. 09 지시서의 읽기 전용 문구보다 상위 명세의 입력 규칙과 기존 기능 유지 원칙을 우선했어요. 운영 시간·공간 종류·예약 방식·팀 지점의 선택값은 서버 HTML에도 바로 표시해요.

공간 표는 종류별로 묶고 이름순으로 보여줘요. 각 행의 동작 메뉴에 고치기·이용 대상·보관 또는 되살리기가 있어요. 이용 대상은 대화상자의 해당 제목으로 포커스를 옮기며 닫으면 지속되는 행 메뉴 버튼으로 돌아가요. 권한이 없는 일반 정보·이용 대상 구역은 계속 읽기 전용이고, 보관·되살리기는 권한이 없으면 실행할 수 없어요. 저장 후 새로 읽을 때 기존 표를 유지해요.

운영 시간은 일곱 요일을 모두 저장하고 휴무와 30분 단위 시각을 선택해요. 시간대는 변경하지 않아요. 층 번호는 지점 안에서 중복될 수 없고, 자동 순서는 빈 지점에서 0으로 시작해요. 공간 이름은 같은 층의 보관되지 않은 공간끼리 대소문자를 무시하고 유일해요. `0006_space-admin.sql`이 이 부분 유니크 인덱스를 추가해요. 기존 활성 공간 이름에 중복이 있으면 마이그레이션 전에 확인하고 직접 판단해야 하며 자동으로 이름을 바꾸거나 삭제하지 않아요.

회의실·세미나실·폰부스만 예약 가능 여부를 바꿀 수 있어요. 라운지와 데스크 구역 자체는 예약하지 않으며, 좌석이 있는 구역은 멤버 화면에서 개별 좌석을 예약해요. 운영자 공간 목록에서는 좌석 개수만 표시하고 좌석을 직접 고치지 않아요. 공간은 삭제 대신 보관하고, 공간 행을 잠근 뒤 끝나지 않은 확정 예약이 있으면 보관과 예약 불가 변경을 거절해요. 데스크 구역을 보관할 때는 그 구역의 좌석 예약도 함께 세어요. 보관한 공간의 일반 정보는 고칠 수 있지만 이용 대상은 복원 후 바꿔요. 보관한 동안 다른 공간이 같은 이름을 쓰면 복원도 거절해요. 기존 예약을 취소하거나 이름을 바꾸는 일을 자동으로 하지 않아요.

층의 이용 대상을 지정한 팀으로 바꾸면 공간 설정을 같은 트랜잭션에서 정리해요. 모두 허용하던 공간은 층 설정을 따르고, 지정 팀 공간은 층과 겹치는 팀만 남겨요. 남은 팀이 없으면 닫힘으로 바꾸고 화면에 어떤 공간이 바뀌었는지 알려줘요. 보관된 공간과 좌석도 함께 정리하며 기존 예약은 유지해요. 층을 닫을 때는 공간 설정을 그대로 보존해 다시 열 수 있어요. 팀 검색은 이름과 주 이용 지점만 보여주며 회원 목록·담당자 연락처는 조회하지 않아요.

저장은 공통 mutation 잠금으로 중복 제출을 막고 성공 뒤 서버 정보를 새로 읽어요. 공간 수정·보관·복원·공간 이용 대상 변경 이벤트는 커밋 뒤 발행해요. 층 변경 이벤트, 실시간 구독, 평면도 편집, 점검 등록, 역할 설정 화면은 아직 없어요.

수동 확인은 관리자 로그인 → 강남점 6층에 회의실 추가 → 멤버로 그 회의실 예약 → 관리자로 보관 시도(거절) → 예약 취소 뒤 보관 → 8층 이용 대상에 그로스팀 추가 순서예요. 시드를 다시 실행하면 시드 고정 ID의 지점·층·공간 설정을 원본으로 맞추므로, 해당 대상에 한 관리 변경을 유지하려면 재실행 전에 확인해 주세요.

09 화면의 저장 동작은 **운영자로 로그인 → 강남점 → 평일 적용 → 저장 → 7층 → 공간 동작 메뉴** 순서로 별도 수동 확인해요. 이번 개발용 Neon 브라우저 검증은 로그인·조회·이동·메뉴·대화상자 확인까지만 하며 예약·취소·저장·초대 전송은 실행하지 않아요. 07–09에는 스키마·마이그레이션·시드 변경이나 새 패키지 설치가 없어요.

## 공간 사진과 공통 화면

사진 원본 29개는 `public/seed/photos/`의 1200×750 WebP 파일이에요. `0007_space-photos.sql`은 공간 사진 테이블과 지점 대표 사진 컬럼을 추가해요. `docs/spec/examples/seed-photos.json`을 별도 strict 스키마로 검증하고, 기존 시드 트랜잭션 안에서 공간 사진 65행과 지점 대표 사진 5개를 넣어요. 0번 사진만 대표 사진이며, 사진 순서에 빈칸이 있어도 다른 사진을 대신 대표로 쓰지 않아요.

다시 실행하면 **시드 공간 전체**의 빠진 사진과 시드 지점의 빠진 대표 사진을 정리해요. 시드 밖 사진과 지점은 보존해요. 사진을 교체하려면 로컬 파일과 `seed-photos.json`의 경로·설명을 함께 고치고 마이그레이션 적용 후 시드를 실행해요. 업로드·외부 이미지 저장소는 없고, 사진 경로는 소문자 로컬 경로만 허용해요. 대체 글은 Unicode 문자 수로 1–120자예요. 공개 정적 자산이므로 파일 URL 자체를 비밀로 보호하는 기능은 아니에요.

`SpacePhoto`는 종류별 자리 표시·로딩·실패 상태를 같은 크기로 그리고, `PhotoGallery`는 scroll-snap과 실제 스크롤 위치를 사용해요. 사진 크게 보기의 키보드·닫기 후 포커스 복원을 지원해요. 모든 사진은 `next/image`이며 바로 보이는 큰 첫 사진만 먼저 읽어요. `SegmentedLinks`, `StatusLine`, `BookingChip`, `SectionLabel`도 공용으로 사용해요. 머리글은 60px, 제목은 26/700, 카드는 14px 모서리와 `shadow-card` 토큰이에요.

사진 조회는 접근을 허용한 공간 ID로만 실행해요. 제한 공간은 여전히 `kind`, `id`, `type` 세 필드이고, 지금 접근할 수 없어도 본인이 만든 예약에 붙는 사진만 예외예요. 운영자 권한 판정과 취소 대상 조회에는 사진을 추가하지 않았어요.

### 10 완료 시점의 조회 예산

사진 추가 전후 문장 수는 같아요. 대괄호는 각 순차 단계에서 병렬 실행한 문장 수예요.

| 조회             | 이전 → 사진 추가 후   |
| ---------------- | --------------------- |
| 층 목록          | `[6,4]` → `[6,4]`     |
| 공간 상세        | `[6,6]` → `[6,6]`     |
| 지점 줄          | `[6]` → `[6]`         |
| 지점 목록        | `[6,1]` → `[6,1]`     |
| 홈 빈 공간       | `[1,5,3]` → `[1,5,3]` |
| 홈 다가오는 예약 | `[1]` → `[1]`         |
| 내 예약          | `[2,1]` → `[2,1]`     |

공간 상세의 사진은 공간 정보 SQL에 JOIN·집계하고, 본인 예약 사진은 기존 예약 SQL에 JOIN해요. 여러 층·팀이 늘어도 SQL 수가 반복 증가하지 않는 회귀 검사를 유지해요.

이번 10–12 작업은 지시서의 “실제 DB 없음” 전제와 달리, 사용자가 승인한 개발용 Neon에 **전체 자동 검사 후 한 번** 마이그레이션과 시드를 적용해요. 시드는 사진뿐 아니라 기존 시드 대상 설정·소속·허용 팀·예약 날짜도 원본으로 맞춰요. 기존 인증 완료 계정과 `test1@ai.com`–`test20@ai.com`, 시드 밖 데이터는 보존하고 비밀번호 초기화 옵션은 쓰지 않아요. 브라우저에서는 로그인·조회·선택·이동만 확인하며 실제 예약·취소·설정 저장은 별도 수동 확인 대상이에요.

## 검사와 CI

### 11 완료 시점의 조회와 검증

`lint`, `typecheck`, 기본·LA 시간대 전체 **123개 파일·2,317개 테스트**, DB/Auth 값을 비운 `build`, `build-storybook`, Chromium E2E 7개가 모두 통과했어요. 건너뛴 테스트는 없어요. 초기 전체 검사에서 나온 `select-ssr`의 펼침 전 선택 상자 기대값은 실제 입력이 보이는 예약 줄로 옮겨 기존 텍스트 단언을 유지하고, 패널의 접힌 SSR 검사도 추가했어요. 이동 중 보기 변경 구현의 effect 상태 갱신은 작업 대기 ref로 바꿔 lint 오류를 해결했어요. 실제 Neon 앱의 900px 일정 높이와 읽기 전용 이동 확인은 12 및 DB 적용 뒤에 진행해요.

| 조회      | 10 → 11 단계별 SQL                           |
| --------- | -------------------------------------------- |
| 지점 줄   | `[6]` → `[6,1]` (본인의 예약 날짜 읽기 추가) |
| 층 목록   | `[6,4]` → `[6,4]`                            |
| 공간 상세 | `[6,6]` → `[6,6]`                            |

예약 액션·권한·노출·EXCLUDE와 기존 예산 단언은 유지했어요. 기존 UI 검사는 바뀐 화면과 동일한 동작을 확인하도록 갱신했어요: `booking-components`, `day-grid-components`는 접힌 시간·제목을 펼친 뒤 기존 입력·오류·한도·중복 제출을 확인해요. `booking-pages`, `branch-layout`는 쿠키를 읽는 Suspense와 형제 조회를 확인하고, `floor-navigation`, `space-detail-container`는 목록 모드를 명시해 기존 낙관적 선택·포커스·단일 상세 검사를 유지해요. `floor-member-screen`은 상태 배지·중복 건수 대신 한 줄 문구를, `photo-screen-integration`은 72×54/56×44와 160/120 사진 크기를, `skeletons`는 두 보기의 CSS 및 새 네 구역을 확인해요. 기존 DB 기대값에는 `bookingDates: []`만 추가했고 보안 단언을 줄이지 않았어요.

### 화면 선표시·점진 로딩 개선

데이터 없이 알 수 있는 제목·링크·요일·표 머리는 먼저 보여주고, 이름·건수·예약·권한별 동작만 기다리도록 바꿨어요. 홈과 지점 목록, 팀 시작·목록, 인증·운영자 홈은 실제 고정 틀과 데이터 영역을 분리해요. 팀 상세와 운영자 지점·층의 로딩 화면도 비민감 표 머리는 바로 보여줘요. 기존 세션 가드와 조회 함수의 권한 확인은 그대로예요.

내 예약 달력은 **고정 틀 → 홈 지점 시간대의 실제 날짜 → 예약 정보** 순서예요. 날짜 링크와 월 이동은 예약을 기다리지 않고, 건수·조각·선택일 패널이 같은 Promise를 사용해요. 층 달력도 운영 시간·접근 가능한 층을 받은 뒤 먼저 사용하고 예약 점만 나중에 붙여요. 모르는 예약을 0건·없음으로 표시하지 않아요. 빠른 월 이동 중 고른 날짜는 마지막 값만 이동 완료 뒤 URL에 합치며, 화면 이탈·Activity 숨김·뒤로 가기는 대기 중인 URL 변경보다 우선해요.

지점 화면에서 나갈 때의 `branchId.toLowerCase()` 오류는 보존된 레이아웃이 전역 `useParams()`를 읽던 문제였어요. 서버의 지점 id와 해당 레이아웃의 segments로 범위를 고정하고, 외부 경로의 query와 늦은 응답이 이전 초안이나 현재 URL을 건드리지 않게 했어요. 보기 변경의 임시 값도 숨김·이탈 때 폐기해 복귀 URL과 표시가 어긋나지 않아요.

시간표의 행·블록, 예약 양식의 필드·배치, 내 예약 달력의 도구 줄·예약 표시·선택일 패널을 표시 컴포넌트로 나눴어요. 선택·검증·mutation·키보드·스크롤을 별도 상태 저장소로 옮기지 않았고, 표시 컴포넌트는 값과 콜백만 받아요. Workspace의 범위·포커스 도우미도 기존 Context 하나를 유지해요. 새 패키지·HTTP API·캐시·DB 변경은 없어요.

팀 시작 조회는 선택 단계에서 받은 초대, 생성 단계에서 지점만 읽고, 가입 단계에서는 유효한 검색어가 있을 때 필요한 자료만 읽어요. 잘못되거나 빈 검색어이면 세션 확인 뒤 DAL을 호출하지 않아요. 기존 mode 없는 완결형 조회 계약은 유지해요.

기존 화면 테스트는 새 고정 틀 아래의 Suspense를 찾아 같은 가드·리다이렉트·비노출 단언을 유지하도록 갱신했어요. 날짜 점의 접근성 이름은 실제 링크의 `aria-labelledby`로 검사하고, Next.js mock은 레이아웃 segments와 실제 native-history 구독을 반영해요. 액션·권한·DB 제약 테스트는 그대로예요. 새 검사는 metadata와 예약 지연, 링크 DOM·포커스 유지, 월·날짜 역순 응답과 Activity 복귀, 팀 모드별 불필요 DAL 미호출을 다뤄요.

2026-10-08 최종 검사: Node 22.23.3에서 lint·typecheck, **147개 파일·2,612개 테스트**(기본·LA 시간대 각각), DB/Auth/OAuth 값을 비운 build, Storybook build, 기존 Chromium E2E **7개**가 모두 통과했어요. 건너뛴 테스트는 없어요. 기준 검사 2,547개에서 65개를 더했고 기존 jsdom 문서 이동·Storybook 번들 경고는 남아 있어요. DB 스키마·마이그레이션·액션·권한·패키지에는 변경이 없어요.

기존 개발 서버의 가상 회원으로 1440×1000·768×1024·390×844에서 로그인·조회·선택·이동만 확인했어요. 층 → 홈·내 예약·팀 → 뒤로 가기와 강남 → 성수 → 뒤로 가기에서 오류 없이 작성 중인 제목이 유지됐어요. 홈의 고정 카드 제목·링크가 조회 전에 표시되고, 월 이동 중 실제 새 달과 예약 로딩 안내가 보이며, 대기 중 선택한 날짜가 완료 뒤 URL에 반영되는 것도 확인했어요. 연속 월 이동, 범위 끝의 비활성 이동, 모바일 날짜 선택기와 아래 시트(약 717px), 가로 넘침 없음, 모바일 뒤로 가기·전체 새로고침을 확인했어요. 브라우저 오류·경고 로그는 없었어요. 개발 모드의 Next.js 도구 배지가 모바일 홈 링크 중심을 덮는 경우는 키보드로 확인했으며 앱 설정은 바꾸지 않았어요.

지연·역순 응답의 모든 조합, 달력 Activity 숨김 중 외부 이동, 시트의 단일 DOM·애니메이션 유지와 늦은 성공은 자동 회귀 검사로 확인했어요. 이번 실제 브라우저에서 인위적인 응답 지연·애니메이션 횟수 측정까지 다시 하지는 않았어요. 실제 예약·취소·설정 저장·운영자 저장 흐름과 PostgreSQL 다중 연결 동시성은 **확인 못 함**이에요. 인증 외 DB 쓰기·마이그레이션·시드·환경 파일 직접 읽기/수정·Jira·push·배포는 하지 않았어요.

### 가상 지점 확장과 예약 초안 상태 정리

2026-10-08에 홍대·여의도·판교를 추가했어요. 신규 지점은 모두 공개 2개 층과 공간 8개(예약 가능 6개)를 갖고, 기존 공개 사진을 재사용해요. 빈 DB 전체 시드 기준은 5지점·11층·71공간·예약 21개·점검 4개·공간 사진 65행·대표 사진 5개예요. 새 패키지·스키마·마이그레이션은 없어요.

공유 상태는 전부 교체하지 않았어요. 예약 제목·예약 방식·시간 구간만 Workspace마다 생성한 Zustand vanilla store에서 selector로 읽어요. 기존 Context는 저장소 참조와 라우팅을 전달하고, URL·낙관적 이동·서버 승인·Suspense·포커스는 React에 남아요. 표시 시계와 저빈도 보기 설정 Context도 유지해요. 전역 singleton·persist·공간별 초안 보관함은 만들지 않았어요.

제목 입력은 날짜 줄·시간표 구간·시트 컨테이너 구독자를 다시 렌더링하지 않아요. 보기·상세 전환과 Activity 숨김은 초안을 유지하고, 공간·층·날짜 변경은 초기화해요. 제출 당시 범위로 성공 처리를 고정해 다른 공간·날짜로 이동한 폼의 늦은 응답이 새 입력을 지우지 못하게 했어요. 성공한 로그아웃과 운영자 계정 전환은 전체 문서 이동으로 이전 계정의 클라이언트 상태를 버려요.

추가 전용 시드는 잘못된 범위·중복·`--reset-passwords` 병용을 거절하고, 기존 인증 완료 계정만 조회해요. 기존 지점의 고정 ID 부모 관계·필수 행·사진 순서·운영자 소속이 불완전하면 자동 복구하지 않아요. 무옵션 전체 시드의 기존 동작은 유지돼요. 추가 모드에는 인증을 초기화하지 않으므로 `AUTH_SECRET`이 필요하지 않으며, 새 평면도까지 포함하는 지점 묶음은 지원하지 않아요.

현재 개발용 Neon은 기존 환경 로더와 정확한 허용 호스트로 **새 3개 지점만** 적용했어요. 마이그레이션 이력 8개가 저장소와 일치하고 고정 ID 충돌·필수 계정 검사가 통과한 뒤, 같은 트랜잭션에서 기존 21개 앱 테이블의 217개 행 내용 지문을 전후 대조했어요. 기존 두 지점·인증 계정·소속·예약·사진·평면도와 테스트 계정 20개는 모두 보존됐어요. 신규 3지점·6층·24공간·24사진·3운영자 소속·12예약·3점검만 추가됐어요. 지점별 대표 사진·사진 순서·예약 및 점검의 운영일/시각도 원본과 대조했고, 다음 날 기준 재실행도 변경이 없었어요. 커밋 후 재조회에서 지점 5개·테스트 계정 20개·추가 예정 0개를 확인했어요. 전체 시드·비밀번호 초기화·마이그레이션은 실행하지 않았어요.

1440×1000·768×1024·390×844에서 기존 회원의 지점 5개·사진·운영 시간, 새 지점 사이의 이동, 시간 선택, 시간표↔목록·상세 전환, 홈 이탈 후 뒤로 가기와 제목/구간 유지를 확인했어요. 태블릿·모바일 시트는 하나만 표시되고 가로 넘침이 없었으며, 닫은 뒤 선택했던 공간 링크로 포커스가 돌아왔어요. 다른 공간에서는 이전 제목·구간이 비워졌어요. 회원 로그아웃과 일반 회원의 운영자 계정 전환, 기존 운영자의 5개 운영 지점 조회도 확인했어요. 브라우저 실행 오류나 Suspense 경고는 없었지만 기존 지점 대표 이미지의 LCP/eager-loading 권고 1건은 남아 있어요.

실제 예약·취소·기본 지점 변경·관리 설정 저장은 실행하지 않았어요. 지연·역순 응답과 시트 단일 DOM·애니메이션은 자동 회귀 검사로 확인했고, 실제 브라우저에서 인위적 응답 지연이나 애니메이션 횟수 측정까지 다시 하지는 않았어요. 실제 PostgreSQL 다중 연결 경합은 **확인 못 함**이에요. 환경 파일 직접 열람·수정, 전체 시드, 마이그레이션, Jira·push·배포는 하지 않았어요.

### 예약 2차: 사용 인원과 공간 거르기

시간 예약에 사용 인원을 선택해서 적을 수 있어요. 정원이 있는 공간은 정원까지, 정원이 없는 공간은 500명까지이며 입력하지 않아도 예약돼요. 서버는 접근 확인 뒤와 공간 잠금 뒤에 정원을 검사해요. 예약 제목을 볼 수 없는 사람에게는 사용 인원도 전달하지 않아요.

층 도구 줄의 인원 조건(2–50명)은 URL의 `people`에 보관해요. 목록과 시간표를 클라이언트에서 함께 거르며 별도 조회는 하지 않아요. 이미 고른 공간은 유지하고, 좌석이 있는 데스크 구역은 인원 조건에서 제외해요. 조건의 인원은 아직 직접 수정하지 않은 예약 양식의 기본값으로만 사용해요. 제목·방식·시간과 같은 범위의 Zustand 초안에 저장하며 보기·상세 전환에서는 유지하고, 다른 공간·층·날짜로 이동하면 비워요.

예약 2차 시드 자료는 전체를 strict 검증한 뒤 사용해요. 전체 시드와 새 지점의 예약 INSERT에는 지정된 사용 인원을 넣고, 이미 추가된 지점은 `--branches`로 덮어쓰지 않아요. 기존 DB에서는 위의 `--booking-round2` 모드로 지정된 여섯 예약의 사용 인원과 참석자·좌석 예약·좌석 점검·미래 미리 알림을 함께 보완해요.

### 좌석 예약

좌석이 있는 오픈 데스크는 구역 대신 자리를 예약해요. 지점 현지 시각 13시를 기준으로 오전·오후를 나누고, 둘 다 운영하는 날에는 종일도 골라요. 오전·오후는 끝나기 전까지, 종일은 오전이 끝나기 전까지 예약할 수 있어요. 같은 사람은 지점과 개인/팀 방식을 합쳐 겹치는 시간에 한 자리만 예약할 수 있고, 좌석 시간은 회의실의 하루 시간 한도에서 제외돼요.

시간표의 구간이나 공간 이름을 누르면 좌석 배치도가 열려요. 평면도의 좌석 위치만 서버에서 줄·칸으로 바꾸며, 위치가 없는 자리는 이름순으로 여섯 칸씩 이어져요. 다른 이용자의 신원은 보내지 않고 빈 자리·예약됨·내 자리·점검·예약 불가 상태만 보여줘요. 구역의 이용 대상과 점검도 모든 좌석에 적용해요. 내 예약과 홈의 좌석 링크는 개별 좌석이 아닌 구역 상세로 연결돼요.

빈 DB 전체 시드 기준 예약은 30개, 점검은 5개예요. 실제 개발 DB 전체 건수와는 다른 값이며, 이번 예약 2차의 실DB 적용은 전체 시드가 아닌 추가 전용 모드로만 해요.

### 예약 참석자

시간 예약에 나 외에 참석자 20명까지 넣을 수 있어요. 같은 팀 사람은 이름·이메일 일부로, 다른 사람은 전체 이메일 일치로만 찾아요. 새 참석자는 이메일 인증을 마친 계정이어야 하며, 같은 팀이 아닌 손님은 전체 이메일을 증명해 최대 5명까지 초대해요. 사용 인원을 적었다면 나와 참석자를 합친 수 이상이어야 해요.

`GET /api/participants/search`는 로그인한 사람만 사용할 수 있고 응답은 `private, no-store`예요. 사용자별 분당 전체 검색 30회, `@`가 포함된 검색 10회로 제한하며 초과하면 `429`와 `Retry-After`를 반환해요. 응답은 가린 이메일만 담고, 외부 참석자의 전체 이메일은 제출용 초안에만 잠시 둬요. 배포 전에는 메모리 제한기의 다중 인스턴스 한계와 검색 URL 로그의 이메일 마스킹을 점검해야 해요.

초대받은 예약은 내 예약·달력·홈에 나타나며 사진과 공간 이동 링크는 제공하지 않아요. 예약이 끝나기 전에는 “참석 안 함”으로 나갈 수 있어요. 초대받은 시간은 내 예약 한도나 층 날짜 줄의 예약 점에 포함하지 않아요.

### 예약 알림

머리글의 종과 `/notifications`에서 초대·취소·참석 취소·시간 변경·참석자 제외 알림을 확인해요. 시간 예약의 시작 30·10·5분 전과 시작 시각은 예약 저장 트랜잭션에서 미리 넣으며, 별도 cron이나 읽을 때 쓰기는 없어요. 좌석 예약에는 미리 알림을 만들지 않아요. 시드 시간 예약도 미래 미리 알림을 만들어요.

`GET /api/notifications`는 로그인한 본인의 공개된 알림만 `private, no-store`로 반환해요. 같은 예약의 미리 알림은 공개된 최신 한 건만 세고, 예약 종료 시각부터 목록·건수·읽음 처리 대상에서 빠져요. 미래 알림은 다음 공개 시각 `nextAt`만 알려요. 요약은 1단계 3문장, 전체 목록은 1단계 2문장이에요.

종은 60초마다, 창으로 돌아왔을 때, 다음 공개 시각에 맞춰 다시 읽어요. 숨겨진 탭이나 10분 동안 입력이 없는 탭에서는 주기 조회를 멈춰요. 최초 응답의 알림은 토스트로 띄우지 않고, 이전 응답 이후 공개된 미확인 알림만 띄워요. 같은 예약의 미리 알림 토스트는 하나로 교체돼요. 읽음 처리는 낙관적으로 표시하며 실패 시 복구해요. 운영자 화면에는 종이 없고, 모바일 종은 알림 페이지로 이동해요.

### 예약 바꾸기

내 예약 목록·달력의 본인 시간 예약에서 “바꾸기”를 눌러 `/bookings/[bookingId]/edit`로 이동해요. 끝나지 않은 확정 예약의 시간·사용 인원·참석자·제목을 바꿀 수 있어요. 공간·날짜·개인/팀 방식은 고정이고, 좌석 예약과 초대받은 예약은 수정하지 못해요. 진행 중인 예약은 시간만 잠겨 있으며 나머지 입력은 고칠 수 있어요.

시간이 바뀔 때만 시간 규칙·한도·점검을 다시 검사하고, 겹침은 기존 DB EXCLUDE 제약으로 막아요. 인원과 참석자는 항상 현재 정원으로 검사하므로 정원이 줄어든 예약은 초과 값을 직접 줄여야 해요. 기존 참석자에게 이메일 증명을 다시 요구하지 않지만 전체 명단의 외부 참석자 5명 제한은 다시 검사해요.

새 참석자는 초대 알림, 빠진 사람은 그 사람이 알던 시간으로 제외 알림을 받아요. 시간 변경 시 남아 있던 참석자에게 변경 알림을 보내고 옛 미리 알림을 새 시각으로 교체해요. 제목·인원만 바꾸면 알림은 만들지 않아요. 오래된 수정 화면이 중간에 “참석 안 함”으로 나간 사람을 자동 재초대하지 않으며, 다시 초대하려면 새로고침한 뒤 추가해요.

수정 화면의 초안은 화면 내부에 두고 충돌 후 새로 읽어도 유지해요. 기존 시간이 현재 운영 시간 밖이거나 정원이 1명으로 줄었더라도 원래 값을 숨기거나 참석자를 자동 삭제하지 않고 필요한 수정 입력을 제공해요.

### 예약 2차 검증과 개발 DB 적용 기록 — 2026-10-08

14–18 구현과 최종 모바일 좌석 영역 보완 후 `lint`, `typecheck`, 기본·LA 시간대 각각 **211개 파일·3,420개 테스트**, DB/Auth/OAuth 값을 비운 `build`, `build-storybook`, Chromium E2E **10개**를 통과했어요. `db:generate`는 무변경이에요. 기존 권한·민감정보 비노출·조회 예산 검사는 유지했어요.

승인된 개발용 Neon에 추가형 마이그레이션 네 개와 `--booking-round2`만 적용했어요. 사용 인원 6건을 보완하고 참석자 5행·좌석 예약 9건·점검 1건·미래 미리 알림 44건을 추가했어요. 기존 행 해시 비교에서 허용한 인원 외 변경·삭제가 없었고, 전용 시드 재실행도 완전히 무변경이었어요. 실제 DB 전체 예약은 **34건**으로 빈 DB 전체 시드 30건과 달라요. 지난 예약 날짜, 기존 계정·비밀번호·소속·사진·평면도는 그대로예요. 로컬 완료 표식은 보관해 주세요.

기존 계정으로 데스크톱·태블릿·모바일의 조회·선택·이동, 좌석 시트, 초대된 예약, 수정 화면·참석자 검색, 알림 화면을 확인했어요. 실제 예약·수정 저장·취소·참석 취소·알림 읽음과 PostgreSQL 다중 연결 경합은 **확인 못 함**이에요. 두 계정으로 해당 쓰기 흐름을 별도로 확인해 주세요. 단계별 검사, SQL 예산 표, 적용 전후 비교와 화면 검증 범위는 [예약 2차 인계 기록](docs/codex/booking-round2-delivery.md)에 있어요. 새 패키지 설치·환경 파일 직접 열람/수정·Jira·push·배포는 하지 않았어요.

### 다시 실행하기

```sh
pnpm lint && pnpm typecheck && pnpm test && pnpm build
TZ=UTC pnpm test
TZ=America/Los_Angeles pnpm test
pnpm db:generate

pnpm test:e2e
```

DB 테스트는 메모리 PGlite에 실제 SQL 마이그레이션을 적용해요. 예약 EXCLUDE·경계·부분 유니크·참조 제약, DAL 트랜잭션, 인증 세션·계정의 사용자 삭제 연쇄와 제공자 계정 유니크 제약을 확인해요. 권한 기본값·역할 합집합·접근 교집합, 액션 순서·오류 변환, 평면도 스키마, 실시간 메모리 구현도 검사해요.

인증 통합 테스트는 PGlite와 메모리 메일로 가입→인증→로그인→로그아웃, 중복 가입 응답, 계정 선점 방지, 재설정 후 기존 세션 폐기, 운영자 생성과 비밀번호 재발급을 검사해요. 소셜 경로는 테스트 제공자의 토큰 검증·사용자 정보를 대체해 외부 왕복 없이 확인해요. UI 테스트는 입력 오류·접근성 연결·중복 제출·메일 불가 안내·60초 대기·오류 문구를 확인해요.

팀 테스트도 실제 마이그레이션을 적용한 PGlite와 메모리 메일을 사용해요. 제약 11–14, 팀 생성·가입 요청·초대, 권한·한도·만료, 중복 처리·교차 정리·기존 역할 보존, 롤백, 응답의 민감 필드와 관리자 전용 조회 분리를 검사해요. SQL 기록으로 잠금 순서와 pending 조건이 있는 `UPDATE … RETURNING`을 확인해요. PGlite는 단일 연결이므로 실제 PostgreSQL 다중 세션의 교착 상태까지 검증하는 것은 아니에요. 팀 화면은 컴포넌트 테스트를 추가하고 기존 E2E는 회귀 검사로 유지해요.

시드 테스트는 원본 파일의 strict 검증·참조, 행 수·반복 실행·운영일 이동·접근 범위, 계정 로그인·기존 비밀번호 보존·명시적 초기화·전체 롤백을 확인해요. 원본 밖의 예약과 겹칠 때 건너뛰는 동작, 기존 게시 평면도 보존과 실행 환경 차단도 검사해요. 시간 도우미는 서울의 자정과 월·연도 경계, 뉴욕의 23시간·25시간짜리 날과 중복·존재하지 않는 현지 시각을 검사하며 `TZ=UTC`와 `TZ=America/Los_Angeles`에서도 같은 결과를 내야 해요. PGlite 검사는 실제 Neon에 시드를 넣지 않아요.

예약 테스트는 제약 15–16, 시간·한도·접근 규칙, 실제 생성·취소·재예약과 SQL 잠금 순서, 이벤트 발행 실패, 응답에서 공간 정보·제목 누락을 확인해요. 화면 테스트는 실제 선택 상자·타임라인·취소 대화상자·중복 제출 방지와 페이지 내부 Suspense를 검사해요. 예약 겹침은 실제 마이그레이션의 EXCLUDE 오류로 확인하며 실제 다중 연결 부하를 재현한 것으로 보고하지 않아요.

운영자 테스트는 제약 17, 실제 대상 지점의 소속·권한, 보관·복원·예약 중 변경 차단, 층 허용 팀 변경과 공간 조정의 원자성, 조정 전후 접근 동등성을 검사해요. 관리 조회의 필드 제한, 7일 운영 시간 입력, 접근 설정과 팀 검색, 페이지별 세션 가드도 확인해요. 이름·주소의 NUL 문자는 PostgreSQL에 저장할 수 없어 입력 검증에서 거절해요.

Playwright는 가짜 비밀 키와 실제 연결할 수 없는 DB 주소로 production 서버를 띄워 비로그인 홈의 로그인 안내, 안전한 `next`, 메일 불가 안내, 운영자 로그인과 키보드 이동을 검사해요. 이 검사는 실제 가입·로그인이나 OAuth 왕복 검증이 아니에요. Storybook은 docs 애드온만 사용하므로 단위 테스트와 독립적이에요.

GitHub Actions는 `main` push와 pull request에서 Node 22·pnpm 12.8.1, pnpm 저장소 캐시와 고정 lockfile 설치로 `lint`, `typecheck`, `test`, `build`를 실행해요. 실제 DB나 인증 비밀 값은 쓰지 않아요. Playwright는 로컬 검사로 두고 CI에는 넣지 않았어요. Actions 설치 방식은 공식 [checkout](https://github.com/actions/checkout)과 [pnpm/setup](https://github.com/pnpm/setup) 안내를 따랐어요. 원격 저장소에 push한 뒤 CI 실행 결과는 별도로 확인해야 해요.

새 개발 DB에서는 위 준비 절차에 따라 마이그레이션을 적용해요. 브라우저의 가입·메일 인증·재설정, Google·GitHub OAuth 왕복, 실제 DB를 쓰는 운영자 CLI는 사람이 별도로 확인해야 해요. 외부 메일 발송·push·배포는 이 작업에 포함하지 않아요.

## 팀 채팅

레일의 팀 아이콘과 사이드바의 `# 일반`에서 팀원끼리 메시지를 읽고 보내요. `/messages`는 참여한 스페이스와 채널 목록이에요. 모바일에서는 메시지 탭으로 들어가며, 채널 안에서는 아래 탭 대신 입력창이 보여요. 헤더는 스크롤해도 고정돼요.

팀 소속으로 읽기·쓰기를 확인하며, 운영자도 그 팀원이 아니면 채널을 볼 수 없어요. 채팅 응답과 실시간 이벤트에는 이메일을 넣지 않아요. 메시지는 4000자까지이고, 사용자 → 방 순서로 잠근 트랜잭션에서 번호와 중복 전송을 처리해요.

실시간은 선택 환경 변수 `ABLY_API_KEY`를 서버에 설정하면 켜져요. 환경 파일은 이번 작업에서 읽거나 고치지 않았으므로 `.env.example`과 실행 환경의 이름을 확인해 주세요. 키가 없으면 전송·조회는 동작하지만 다른 사람의 새 메시지는 채널을 다시 열어 확인해야 해요. 브라우저는 앱당 연결 하나를 사용해요. 서버가 발급한 10분 토큰은 본인의 사용자 채널과 읽을 수 있는 방, 현재 선택한 팀 스페이스만 허용해요. 방에는 구독·presence 권한, 스페이스에는 구독 권한만 주며 와일드카드와 발행 권한은 주지 않아요. 팀에서 빠진 뒤 기존 토큰이 만료되기 전까지 최대 10분 실시간 수신이 가능하다는 한계가 있어요. 메모리 요청 제한은 서버가 여러 대일 때 전역 한도를 보장하지 않아요.

실제 개발 DB에 적용하기 전 옛 채팅 테이블이 사용되지 않는지 확인해 주세요. 지시서 20의 두 마이그레이션(`0012`, `0013`)은 사용 전이던 옛 채팅 테이블을 교체하고 기존 팀마다 스페이스와 `일반`을 만들어요. 지시서 21의 `0014`는 읽은 번호를 저장하는 테이블을 추가해요. `pnpm db:migrate` 후 개발용 전체 `pnpm db:seed`는 시드 팀의 대화를 6개·2개로 다시 채우고 기존 전체 시드 규칙대로 시드 데이터를 갱신해요. 기존 데이터가 있는 DB에서 전체 시드는 선택 사항이며, 채팅만 추가하는 명령이 아니에요. 지점 추가·예약 2차 전용 시드는 채팅을 변경하지 않아요. 이 작업 중 실제 마이그레이션과 시드는 실행하지 않아요.

지시서 20 검증(2026-10-08): lint·typecheck 통과, 기본/LA 시간대 각각 232파일·3,672테스트 통과, DB/Auth/Ably 값 없는 build·Storybook build 성공, Chromium E2E 11개 통과, `db:generate` 무변경을 확인했어요. 실제 Neon·Ably 왕복과 로그인한 채널 화면은 확인 못 함이에요. 적용 뒤 두 팀원 계정의 서로 다른 브라우저에서 전송·한글 조합·모바일 입력창을, 팀원이 아닌 계정에서 같은 주소의 404를 확인해 주세요.

### 읽음·이전 메시지·재연결

팀에 들어온 뒤 남이나 시스템이 보낸 메시지부터 안 읽음으로 계산해요. 내 메시지나 재가입 전 대화는 표시하지 않아요. 읽은 번호는 줄어들거나 방의 마지막 번호를 넘지 않아요. 안 읽은 채널은 굵게, 스페이스는 작은 막대로 표시하고 접근성 이름에도 상태를 넣어요. 선택한 스페이스만 실시간으로 맞추고 전체 목록은 창 복귀와 60초 간격으로 읽어요. 숨겨진 탭과 10분 동안 입력이 없는 탭에서는 주기 조회를 멈춰요. 오래된 조회나 전송 응답이 최신 표시를 덮지 않아요.

채널을 열면 처음 안 읽은 메시지에 `새 메시지` 줄을 표시하고, 마지막 메시지를 실제로 보면 1초로 묶어 읽음을 저장해요. 처음 안 읽은 메시지가 너무 멀면 최대 500개까지만 찾고 맨 아래에서 시작해요. 위로 스크롤하면 이전 메시지를 50개씩 붙이며 보던 위치를 유지해요. [TanStack Virtual의 채팅 목록 방식](https://tanstack.com/virtual/latest/docs/chat)을 사용해 줄 높이를 측정하고 화면 근처의 줄만 렌더링해요. 가상 목록 자체는 읽어 주지 않고 별도 알림 영역이 남의 실시간 새 메시지만 안내해요.

처음 채널이 붙을 때, 재연결할 때, 메시지 번호가 건너뛸 때 빠진 번호를 읽어 채워요. 200개를 넘게 놓쳤으면 최근 50개에서 다시 시작하되 내 전송 중 메시지는 남겨요. HTTP 429는 `Retry-After` 뒤 한 번 재시도해요. 본문 없는 `room.activity` 이벤트는 스페이스의 안 읽음 표시만 바꿔요.

오프라인이나 네트워크 오류로 못 보낸 메시지는 방별 메모리 대기열에 남고, 연결 복귀 후 같은 `clientId`로 순서대로 보내요. 앱 안에서 다른 화면으로 옮겨도 이어져요. 서버가 실패 코드를 반환하면 재전송·삭제 또는 로그인 안내를 보여 주며, 전송 한도는 10초 후 이어 보내요. 새로고침·창 닫기는 대기열을 잃으므로 브라우저 이탈 경고를 요청해요. 영구 저장·다른 탭 동기화는 하지 않아요.

조회 예산은 실제 PGlite SQL로 검사해요. `getMyChatNav`는 1단계·1문장, `getChannelView`는 2단계·3문장, `getRoomMessagesPage`는 1단계·2문장이에요. 비로그인·다른 팀·삭제된 스페이스는 목록·메시지·읽음·토큰에서 모두 막아요. 메시지 GET과 목록 GET은 `private, no-store`예요.

기존 테스트를 바꾼 범위와 이유는 다음과 같아요. 나머지 권한·노출·잠금·조회 예산 단언은 유지했어요.

- `constraints`, `seed`, `seed-round2`, `seed-round2-audit`: 옛 채팅 테이블 fixture를 새 스키마로 옮기고 시드 채팅 건수·보호 대상을 추가했어요.
- `app-shell`, `app-shell-streaming`, `member-layout`, `member-nav`, `member-navigation`, `proxy`, E2E: 메시지 경로·메뉴·가드와 무채색 레일 막대 계약을 반영했어요. 기존 인증 화면 스모크는 남겼어요.
- `chat-channel`: 번호 누락 시 전체 새로고침 대신 빠진 메시지를 합치는 동작으로 바꿨어요. 가상 목록은 jsdom에 크기·ResizeObserver 준비를 더했으며, 수동 재전송 검사는 서버 오류로 유지하고 전송 한도의 10초 자동 재시도는 별도 검사해요.
- `chat-actions`, `chat-read-actions`, `realtime`: 커밋 뒤 방 메시지와 본문 없는 스페이스 활동 두 이벤트를 확인하도록 발행 수와 필드를 갱신했어요. 중복 전송·읽음 액션의 추가 발행 금지 단언은 유지했어요.
- `chat-token`과 브라우저 연결 테스트: 선택 스페이스 구독을 추가하고 남의 스페이스 권한 제외를 확인해요. `query-budget`에는 새 채팅 조회의 상한 검사를 추가했어요.

적용 후 두 팀원 계정을 서로 다른 브라우저로 열어 점·굵기 → 새 메시지 줄 → 맨 아래 읽음을 확인해 주세요. 한쪽을 오프라인으로 바꾸고 셋을 보낸 뒤 복구해 전송 순서와 상대 메시지 보충을 확인해 주세요. 로그인한 데스크톱·태블릿·모바일의 실제 가상 스크롤·포커스·한글 입력·Ably 연결과 PostgreSQL 다중 연결 교착 여부는 별도 확인이 필요해요. PGlite와 가짜 Ably 검사는 이를 대신하지 않아요.

지시서 21 최종 검증(2026-10-08): lint·typecheck 통과, 기본/LA 시간대 각각 246파일·3,810테스트 통과(건너뛰기 없음), DB/Auth/Ably 값 없는 build·Storybook build 성공, Chromium E2E 12개 통과, `db:generate` 무변경을 확인했어요. Storybook의 의존성 `use client` 번들 경고와 jsdom의 전체 문서 이동 안내는 있지만 검사 실패는 없어요. 실제 Neon·Ably·로그인한 채팅 화면은 확인 못 함이에요. 새 `.md` 제외 규칙을 유지했고, 작업 중 추가된 이후 지시서의 사용자 문서·환경 예시·시드 자료는 커밋하거나 되돌리지 않았어요.

### 메시지 다듬기 (지시서 22)

메시지에 답장·수정·삭제·리액션을 사용할 수 있어요. 본문은 굵게·기울임·코드·주소·멘션만 해석하고 HTML은 실행하지 않아요. 멘션 입력은 같은 방의 멤버 중에서 고르며, `@모두`는 팀 관리자만 사용할 수 있어요. 삭제된 메시지는 자리만 남고 본문·멘션·리액션을 지워요. 시스템 메시지에는 이런 동작을 제공하지 않아요.

멘션 수는 레일·채널 목록·탭 제목에 표시하고 토스트에서 원문으로 이동해요. 채널이나 스페이스의 알림을 끄면 일반 안 읽음 강조는 사라지지만 멘션 수와 토스트는 유지해요. 입력 중 표시는 방 presence로 전달하며, 받은 이름을 믿지 않고 서버가 확인한 멤버 이름만 표시해요. 토큰 발급 중 구독 대상이 바뀌거나 채널 해제가 실패해도 최신 권한으로 다시 구독할 수 있어요.

리액션 이벤트의 `count/mine/names`로 전체 사용자 집합을 복원할 수 없으므로 이벤트는 재조회 신호로 사용해요. 내 클릭은 낙관적으로 표시하고 실패한 클릭만 되돌려요. 수정·삭제·리액션은 기존 메시지 GET으로 250ms 동안 묶어 보정하고, 다시 연결하면 보이는 구간 → 최신 구간 → 나머지 순서로 읽어요. QueryClient 수명의 대기열은 동시 요청 1개·분당 최대 50회·백그라운드 시작 간격 2초를 지켜요. 같은 요청은 합치고 사용자 스크롤을 우선하며 `429` 재시도도 같은 제한을 받아요. 따라서 GET 한 번의 SQL 예산은 그대로지만 재연결 전체에서는 불러온 구간 수만큼 요청할 수 있어요.

편집 시각은 잠금 아래에서 이전 값보다 최소 1ms 커지도록 저장해요. 두 수정이 같은 시각이거나 앞 요청이 늦게 잠금을 얻어도 오래된 이벤트가 최신 본문을 덮지 않게 하기 위한 보완이며, 별도 버전 컬럼은 추가하지 않았어요. 읽음·음소거도 사용자 → 방(또는 스페이스) → 개인 설정 순서로 잠그고, 발행 실패는 이미 저장한 메시지를 되돌리지 않아요.

`0015` 마이그레이션에 메시지 상세·리액션·멘션·스페이스 음소거와 제약 25–27을 추가했어요. 새 패키지는 없어요. 실제 개발 DB에는 적용하지 않았으며, 전체 시드는 기존 대화를 재작성하므로 보존할 데이터를 확인한 후 적용 여부를 따로 결정해 주세요.

기존 검증은 다음 부분만 새 계약에 맞췄어요: 채팅 DTO fixture에 답장·멘션·수정·삭제·리액션·음소거 필드, 전송 이벤트의 상세 필드와 배치 발행, 자동 완성 입력의 `combobox` 역할, 가상 목록의 별도 가시 구간 인자예요. 한글 조합·전송 순서·목록 무재렌더·읽음 경계·권한·정보 비노출·SQL 예산 검증은 유지했어요. 가짜 Ably와 PGlite 검사는 실제 다중 계정 송수신이나 PostgreSQL 다중 연결 교착 검사를 대신하지 않아요.

지시서 22 검증(2026-10-08): Node 22.23.3에서 lint·typecheck, 기본/LA 시간대 각각 **264파일·4,049테스트**(건너뛰기 없음), DB/Auth/Ably 값 없는 build, Storybook build, Chromium E2E **12개**를 통과했어요. `db:generate` 재실행도 무변경이에요. 실제 Neon 적용·Ably 다중 계정 송수신·로그인한 브라우저 쓰기 흐름은 확인 못 함이에요. 직접 확인할 때는 보존할 데이터를 먼저 확인하고 마이그레이션을 적용한 뒤, 두 팀원으로 답장·편집·삭제 → 멘션·리액션 → 입력 중·음소거 → 연결을 끊은 동안 변경한 메시지 복구 순서로 확인해 주세요.
